## 1. What Realm is

AgentSpaces builds in part on Embabel. A fleet gains when an Embabel application joins it, and gains again when the customer describes its domain as a realm. This document states that relationship, what each side owns, and what a reader may rely on.

The repository's sources describe an Embabel *realm* as a package of meaning. It holds five parts:

- **types**: the domain objects, each with a name, identity keys, typed fields, parent types, and references to other types (`virtualJoins`). The reference console turns each `spine` entry into a string property and a true `userAnchor` into a boolean property, and interprets neither further.
- **producers**: how the realm obtains each object. A producer has a kind: `remote` or `api` (an operation of one of the realm's APIs), `sql` (a datasource and a query), or `compute`, `vector`, `generative`, `aggregate`, `jar`, `source-tree` (the realm's own code serves these).
- **APIs**: the remote operations the producers call, each with its OpenAPI 3.x document.
- **apps**: pages over the objects, served from the realm's base URL.
- **prompts** (a later addition to the format): the texts the realm's agents run, with declared variables.

On disk a realm is a directory tree: `realm.yml`, `types/`, `producers/`, `apis/` (an `apis.yml` and an OpenAPI file per API), `apps/`, and `prompts/`. A console reads one document, the *bundle*: the tree folded into a single YAML 1.2 document with the parts as top-level keys. A realm's own tool produces the bundle. The bundle's `realm:` key carries `name`, `version` (the format version, today `"1"`), `namespace` (the IRI (RFC 3987) namespace of the types, default `urn:realm:<name>#`), `url` (where the realm's apps live), and `description`.

**Where the sources stop.** The sources call the format an Embabel realm, and the Realm Specification addresses the Embabel team. `agentspaces-springai.md` §4 lists the features of Embabel 1.5.2 and names no realm. The repository holds no definition of the realm format from the Embabel project itself. §8 asks who owns the format and its versions.

## 2. The two worlds

A realm answers *what are the objects, and where do they come from*. It knows nothing of peers, leases, takes, or who is on duty. An AgentSpaces group answers *who works on the objects, and how*: its spaces (lanes of typed entries agents write and take), its cards (what each agent, asset, model, and app advertises), its flows, and its rules. It knows nothing of a producer's SQL or an API's token until a configuration tells one of its agents.

A console joins the two. It reads the realm, drafts what the group will need, shows an operator every draft of one import, and carries what the operator approves into the group. The realm's type names become the vocabulary of the fleet: the entries in the lanes, the sentences of the rule books, the cues of the flows, and the goals of the planner. Data moves one way, from the realm into the group, and no console writes back into a realm.

| Concern | The realm (the Embabel side) owns | The AgentSpaces protocol owns | A console owns |
|---|---|---|---|
| Types | names, identity keys, fields, parents, references, the namespace | entry type IRIs as data; it interprets none of them | the drafts of the types and their review |
| Producers | kind, operation, datasource, query, the producer's own code | the `AssetCard` a connector publishes for what it serves (SPEC §6.1a) | the configuration drafts, credential references, approval |
| APIs | the OpenAPI documents and the operations they list | the `FlowManifest` a group's reconciler applies (SPEC §10.3) | the flow drafts and their activation |
| Apps | the pages, their hosting at the realm's URL, the types each page reads | the `AppCard`: `kind`, `shape`, `origin`, `formats`, `ui`, `host` (SPEC §6.1a.2 to §6.1a.4) | admission and publication into the group |
| Prompts | the texts and their variables | nothing | the prompt drafts and their approval |
| The realm's own code | the package that serves the producers no shipped connector serves | the `AgentCard`s its agents publish (SPEC §6.1) | the package catalogue and the deployment |
| Identity | an open question (§8, question 4) | `idpClient` and `host.signOn` `idp` or `none` | the deploying site's identity provider binding |
| The format | its structure and its versions | the registry entry `realm` (`REGISTRY.md`) and §5 | the bundle reader and its report |

## 3. How Embabel fits

Embabel is an Apache 2.0 agent framework on Spring AI. It contributes `@Agent`, `@Action` (with `pre`, `post`, and `cost`), `@AchievesGoal`, `@Condition`, a typed blackboard, and GOAP, Utility, Hybrid, and Supervisor planners that replan after every action. An Embabel agent process and its blackboard live in one JVM (`agentspaces-springai.md` §4).

AgentSpaces builds on that design language:

- SPEC §1 names the Embabel extension, `embabel-agentspaces`, as the first delivery target. An AgentSpace generalizes Embabel's per-process blackboard into a shared, leased, peer-to-peer blackboard that spans many agents on many machines.
- Principle P5 (typed entries, domain-first) follows Embabel's domain-model philosophy: entries are plain records matched by type and template.
- The action contract of SPEC §6.1c (`pre`, `post`, `cost`) carries Embabel's `@Action(pre, post, cost)` onto a card.
- SPEC §10 specifies the extension and its fluent space API, which mirrors Embabel's `ai.withLlm(...).createObject(...)` style.

AgentSpaces benefits when Embabel is in the picture. The `embabel-agentspaces` module publishes each `@Agent` as an `AgentCard` (`EmbabelBinder`, SPEC §10.4). It also generates a typed Embabel agent whose actions invoke the fleet's advertised capabilities (`EmbabelRemoteActions`), and redeploys it as cards arrive and lapse. Embabel's GOAP planner therefore plans over the whole fleet's actions. The module reads Embabel reflectively, so it builds with no Embabel artifact and activates only when Embabel is on the classpath. `EmbabelFleetPlanningTest` (`integration-tests/embabel-it`) and the Party Bus planner exercise it.

A realm benefits AgentSpaces further. The Embabel extension brings an Embabel application's agents into a fleet. A realm brings the domain those agents work on: the types become the fleet's entry vocabulary, the producers become served assets, the APIs become flows, the apps become cards a member finds by discovery, and the prompts become governed texts. The `origin` field of v0.1.32 keeps that provenance visible on every app card.

## 4. The mapping

A console drafts each realm part, an operator approves it, and the console publishes it. The table names the AgentSpaces record that reaches the group. The Realm Specification gives the reference console's own records and approval rules.

| Realm part | AgentSpaces record in the group |
|---|---|
| `realm` (`name`, `version`, `namespace`, `url`) | `origin` on each app card (§5); the namespace of every entry type IRI |
| `types` | entries whose schema name is the type's IRI, the namespace followed by the type name |
| producers of kind `remote` or `api` | an `AssetCard` per operation, from a shipped OpenAPI 3.x and REST connector, configured with the API's location, a credential reference, the operation, the base URL from the document's first server, and the auth scheme |
| producers of kind `sql` | an `AssetCard` per query, from a shipped SQL connector, configured with the datasource and the query |
| producers of any other kind | the `AgentCard`s of the realm's own package, agent kind `<realm>/<producer>`, configured with the producer's fields |
| `apis` | a `FlowManifest` with one code stage per listed operation, on a lane named after the API; the operation's request schema cues each stage, its parameters are cue fields, and its response schema is the result |
| `prompts` | the group's prompt set, carried as a configuration |
| `apps` | an `AppCard` with owner the realm, `origin` `realm`, `formats` with the realm's namespace, and the link `<url>/apps/<file>` (§5); the reference console writes kind `fed` |

A realm names no spaces of its own. The lanes come from the flows its APIs become and from the console's own lanes. A realm imports into one group per import and creates no group.

Before v0.1.32 the reference console wrote apps as kind `realm` and copied the type names into `reads`. ISSUE-AppCardOriginFormats §8.5 and §8.6 move the provenance to `origin` and the type names to `origin.attrs["realm.reads"]`, because SPEC §6.1a.2 defines `reads` as `group/space` pairs (owner answer 2). The reference console's importer writes kind `fed`, since a realm app is a page that an agent of the group feeds when anything does. That choice is the importer's behaviour today (owner answer 3): the protocol ties no kind to an origin, and a later importer may choose another kind, such as `assembled` for a realm page published with its data extracted (SPEC §6.1a.2).

## 5. What `origin` realm promises (normative once accepted)

The key words MUST, SHOULD, and MAY follow BCP 14 (RFC 2119, RFC 8174).

A console MUST import only a bundle whose `realm.version` it reads, and it MUST refuse any other version before it drafts anything. A realm name and an app name match `[A-Za-z0-9._-]+`. A console that meets another name reports it and drafts no card for that app.

An `AppCard` whose `origin.system` is `realm` MUST carry:

- `origin.ref`: `<realm>/<app>`, where `<realm>` is the bundle's `realm.name` and `<app>` the `name` of one entry of its `apps`.
- `origin.version`: `""`. This meaning holds until the owner answers §8 question 2, because `realm.version` is a format version and a realm names no content version today.
- `origin.attrs["realm.format"]`: the bundle's `realm.version`, `"1"` today.
- `origin.attrs["realm.namespace"]`: the bundle's `realm.namespace`, or `urn:realm:<realm>#` when the bundle names none.
- `owner`: `<realm>`.
- `formats`: `text/html` first when the app's file ends in `.html` or `.htm`, then the value of `realm.namespace`.

This section constrains no `kind`. A reader never infers a kind from a realm origin, and never refuses a realm card for its kind.

It MAY carry:

- `origin.attrs["realm.reads"]`: the type names the app entry lists under `reads`, comma-separated without spaces, in the bundle's order. A writer omits it when the entry lists none, and when the value would pass 256 code units, which the console reports.
- `origin.attrs["realm.bundle"]`: proposed, see §8 question 6. A writer omits it until the owner accepts it.

By publishing such a card, the issuer asserts four things under its signature. The app is an entry of the realm bundle it read. The format version, namespace, and type names are the bundle's own. The link resolves under the realm's `url`, or stays `app://<realm>/apps/<file>` when the bundle names no URL. Its console admitted the card before it published it. The card makes no claim that the realm's authors approved the publication, and AgentSpaces carries no signature from them today.

The same realm imported into two groups yields two cards with the same `origin.ref`. That is the intended reading: `group` and `id` tell the cards apart.

While any member of the group is below `wire.appcard=2`, the issuer strips `origin` and `formats` (ISSUE-AppCardOriginFormats FR-7). A stripped realm card then reads as an app of its kind with empty `reads`, and only its `owner` still carries the realm's name, as plain text with no claim of provenance. A realm card that passes the spill threshold keeps `origin` and `formats` on its stub, because neither ever spills (SPEC §6.1a.5).

A reader that relies on a realm origin SHOULD verify it in four steps:

1. Verify the card as any card: the issuer's signature, an unexpired `ttl` (SPEC §6.2), and an issuer that belongs to the group.
2. Check that the group trusts the issuer to publish imports.
3. Check the claim's internal consistency: `owner` equals the first part of `ref`, and `formats` holds the value of `realm.namespace`.
4. Where the reader needs the realm's own word, obtain the bundle from the realm's owner out of band and compare `name`, the app entry, `realm.format`, and `realm.namespace`. §8 question 6 proposes a content-swarm identifier that makes this step a fetch.

A reader that finds a mismatch treats the card as an app of its kind with an unverified origin. The protocol never refuses a card for its origin (ISSUE-AppCardOriginFormats FR-4).

## 6. The lifecycle of an import

1. **Fold.** The Embabel side folds the realm's directories into one bundle, each OpenAPI document inline under its API.
2. **Import.** An operator or a script posts the bundle to a console with the target group and an idempotency key.
3. **Read and draft.** The console reads the bundle and drafts one record per type, producer, API, prompt, and app. Configuration drafts and prompts carry the origin `realm:<name>`. Flow drafts and app rows take the names `realm-<realm>-<api>` and `realm-<realm>-<app>`. The console's answer carries a report: what it could not read, which producer has no API, which package the catalogue still lacks, which app has no URL. The console never guesses a missing piece.
4. **Review and approve.** An operator reviews what one import proposed before approving any of it. The reference console's Configurations and Prompts screens filter by origin; the Realm Specification §6 describes more filtering than the code offers today.
5. **Publish.** The console carries each approved row into the group, and publishes each app card as a signed advertisement under the gate of ISSUE-AppCardOriginFormats FR-7.
6. **Serve.** The shipped connectors publish `AssetCard`s for the operations and queries they serve, the realm's package reads the configurations addressed to it, the reconciler applies the activated flows, and members find the apps by discovery, by origin, and by format.
7. **Import again.** A second import of the same realm drafts new versions of the same records, and nothing published changes without approval. A script may therefore import a realm on every build.
8. **Retire.** An operator retires an app. Its issuer stops reissuing the card, and the card lapses at its `ttl` (SPEC §6.2).

## 7. The worked example

The `claims-ops` realm of the example company Acme Insurance (`acme.example`) holds three types, four producers, one API with three operations, and two apps. Its import yields two REST connector configurations, one SQL connector configuration, and one configuration for the realm's own `claims-ops/riskScore` agent kind. It yields one flow, `realm-claims-ops-claims-api`, with two stages (`listClaims` and `getPayment`; the API's `operation-ids` omits `orderPayment`). It yields two app cards, `claims-desk` and `ledger-view`. ISSUE-AppCardOriginFormats §9.2 shows the `claims-desk` card under v0.1.32. The site's `example.html` walks the import end to end.

## 8. Open questions

1. **Who owns the realm format.** Does the Embabel project publish the realm format, and under what version scheme? The repository holds only the Realm Specification's reading of it.
2. **A content version.** `realm.version` is the format version. Does a realm carry a version of its own content, which `origin.version` would then hold?
3. **Shipped connectors.** Which producer kinds beyond `remote`, `api`, and `sql` should a console serve with shipped connectors, and with which body keys? (The Realm Specification, question 1.)
4. **Identity.** Is a realm-level identity-provider client (`AppCard.idpClient`) the realm's to declare, or the deploying site's? (The Realm Specification, question 4.)
5. **Lanes, actions, and kinds.** Should a realm name the lanes its agents use, the actions its apps may request (`AppCard.actions`), or each app's kind? (The Realm Specification, questions 2 and 3, and ISSUE-AppCardOriginFormats §16 question 3.)
6. **A verifiable origin.** Should the bundle carry a signature by the realm's authors, or should the console publish the bundle on the content swarm and record its CIDv1 under `realm.bundle`, so a reader can fetch the exact bundle and check it?
7. **A machine-readable report.** The import's report is a list of sentences. Does the Embabel side want it as structured data its tool can act on?

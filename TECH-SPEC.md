# AgentSpaces Technical Specification v1.0

**Protocols, Algorithms, and Data Formats of the Reference Implementation**

Companion to `SPEC.md` (v0.1.33; the reference implementation conforms to v0.1.33, and §11 lists where it still trails the design). Where `SPEC.md` states the design normatively, this document describes what the reference implementation in the `agentspaces/` repository actually puts on the wire, byte by byte, and which algorithm runs behind each operation, layer by layer. Every structure named here exists in the code, every constant is quoted from it, §2 explains why this particular set of protocols was selected at all, and §11 records the places where the implementation still trails the design. A developer building a wire-compatible client, auditing the security mechanisms, or extending a layer should read this document beside the source; a developer deciding whether to adopt AgentSpaces should read `WHY.md` first.

## 1. Conventions and Primitives

### 1.1 Encoding

All wire payloads and entry serializations are CBOR (RFC 8949) in the wire encoding of SPEC §9.1 (v0.1.31), produced by the shared codec (`CborCodec`). The canonical form, the form every signature in the system is computed over, is the CBOR serialization of a Java record with fields emitted in declared component order, and of every map inside one with its entries sorted by key in RFC 8949 §4.2.1 order: the shorter UTF-8 encoding first, bytewise between equal lengths (wire v3; `CanonicalMaps` in the codec, `canonical_map` and `canonicalMap` in the clients, applied to map-valued fields, never to the dicts and objects that stand for records). A decoder keeps a map in wire order, which is the sorted order for a map field of a protocol record and the writer's order for an application map. Timestamps (`Instant`) and durations (`Duration`) serialize as ISO-8601 strings (`"2026-08-26T14:02:11Z"`, `"PT15M"`). Since SPEC v0.1.31 a receiver refuses a protocol record that carries a field it does not know, because it re-encodes only the fields it knows and requires the result to equal the bytes it received (SPEC §9.1, rule P1). A new field therefore needs a new wire version or a hint the receiver advertises, as `wire.recordless=1` gates a null record, and removing or reordering fields stays a breaking change. An application document keeps the lenient read and ignores unknown fields. A JSON rendering of every structure exists for logs and debugging; JSON never travels between peers on the core protocol (the A2A gateway, §9.4, speaks JSON-RPC to foreign clients by design).

*The codec's three reads and its encoder (v0.1.31).* `CborCodec` registers three modules, two for the encoder and one for stamps. `CanonicalMaps` sorts every map's entries and, since SPEC v0.1.31, writes every `Set` with its elements in the order of their encodings, so `PeerAdvertisement.roles` no longer follows `Set.copyOf`'s per-JVM order. `CanonicalNumbers` writes a `BigInteger` inside the `long` range as a plain integer, a `BigDecimal` stripped of its trailing zeros with its exponent inside -(2^31-1) to 2^31-1 and its mantissa under its shortest head, and every NaN as `Double.NaN` or `Float.NaN`. `CanonicalStamps` decodes every stamp from its canonical item (§1.4). Since v0.1.31 `WellFormedCbor` refuses in both its modes a bignum whose byte string passes 1000 bytes (`BIGNUM_BYTES`), alone or as a decimal's mantissa, the most Jackson's `StreamReadConstraints` read, and `CanonicalNumbers` refuses to write one, so `checkDocument` and `NodeCodec` refuse it too. The codec then reads in three ways:

- `fromWire(bytes, type)` reads a protocol record from the network. It runs `WellFormedCbor.checkCanonical` over the raw bytes (rules S1 to S12 of SPEC §9.1, the decimal's tag 4 array counted as a nesting level), maps the record with a second mapper whose coercions are all off (`ACCEPT_FLOAT_AS_INT` and `ALLOW_COERCION_OF_SCALARS` off; a `CoercionConfig` that fails text, integer, float, boolean, and binary input into any other logical type and every empty string, array, and object; `FAIL_ON_UNKNOWN_PROPERTIES`, `FAIL_ON_NUMBERS_FOR_ENUMS`, `FAIL_ON_NULL_FOR_PRIMITIVES`, and `FAIL_ON_TRAILING_TOKENS` on; text, `byte[]`, `Instant`, and `Duration` deserializers that take only their own CBOR item, an `Instant` only in the years 0000 to 9999, and a `Duration` only non-negative; and a null refused as a map value and, since v0.1.31, as a list or set element), and requires the record's encoding to equal the bytes received. `WireCodec.decode`, every body decoder in `PeerNode`, `ReplicatedSpace`'s rumor and sync deltas, `AdCache`, `DiscoveryService`, `BlockExchange`, `RevocationRegistry`, `CredentialRevocationRegistry`, `JoinCredentials`, the founding read, `GroupKeyDistributor`, `OrderedTakes`, `RaftLog`, `CapabilityPipes`, `PushSumAggregate`, `GossipLearner`, `SemanticDiscovery`, `RtcSignalCapability`, and the starter's founding read use it. The content swarm's `Messages` and `Content` read through it too since 2026-11-09, and a dispatcher peeks only at the tag before the strict read (SPEC §9.3).
- `fromDocument(bytes, type)` reads an application document such as an entry payload: the same item check, then the lenient mapping that ignores unknown fields. A type annotated `@WireRecord` (`PRef`, `VoteCapability.Proposal`, `VoteCapability.Ballot`) is a protocol record that travels as a payload and reads as `fromWire` reads.
- `fromBytes(bytes, type)` reads what this node persisted, with the item checks of round five alone, so a store written by an earlier 0.5.0 build still opens.

`CborCodec.checkDocument` checks one item against S1 to S12, and `NodeCodec` calls it on every embedded application key and value of a persistent-tree node, so a node admits tags 2, 3, and 4 there and no other tag; a bare link item in a value slot stays the one exception, and `NodeCodec` refuses a link item in a key slot. `PRef.attrs` reads through its own deserializer: any item under `pdt.issued` and `pdt.issuer`, kept raw so the head re-encodes to its bytes, and text under every other key, a null or any other item making the ref undecodable; the 4 KiB bound counts the UTF-8 bytes of the keys and the text values. `WireEncodingTest` and `CborCodecWellFormedTest` pin the codec, and `WireEncodingVectorsTest`, `SpaceWireVectorsTest`, `SignedPeerAdVectorsTest`, and `PRefWireTest` run the vectors of SPEC annex I (`agentspaces/tools/wire-encoding/vectors.json`) through the frame, delta, advertisement, and ref reads.

*The clients' codecs (v0.1.31).* Python (`agentspaces/cbor.py`, `records.py`), TypeScript (`src/cbor.ts`, `src/records.ts`), and Ruby (`lib/agentspaces/cbor.rb`, `schema.rb`) each decode only the wire encoding and write only it. `cbor.loads` (Python, TypeScript) and `CBOR.load` (Ruby) refuse a document that breaks S1 to S12, so every value they return re-encodes to the bytes it came from. A bignum decodes to Python `int`, TypeScript `bigint`, and Ruby `Integer`; a decimal to Python `decimal.Decimal`, TypeScript `CborDecimal` (an exact `exponent` and `mantissa`, normalized when built), and Ruby `BigDecimal`; a float32 to Python `cbor.Float32`, TypeScript `CborFloat32`, and Ruby `AgentSpaces::CBOR::Float32`. Python and Ruby write an integer outside the `long` range as a bignum, Python strips a `Decimal`'s trailing zeros exactly (its `normalize()` rounds past 28 digits), and every client writes only Java's NaN. The schema layer holds every protocol record the client decodes to annex I of the SPEC: Python's `records.decode(raw, name)`, TypeScript's `records.decodeRecord` and `readRecord`, and Ruby's `Schema.load` check the fields, their order, their presence, and their kinds, and refuse a record unless its encoding equals the bytes received. Each client also refuses what Java's record constructors refuse (a null where Java requires a value, an inline payload past 64 KiB, a key epoch below 1, a non-positive dot counter or lease expiry, a certificate with a zero ttl or an encryption key of another length than 32 bytes). Each writes `Digest.digests` sorted through its `canonical_map` or `canonicalMap`, and TypeScript writes `PullResp.deltas`, `SyncDelta.claims`, `EntryRecord.tags`, and `PeerAdvertisement.resourceHints` sorted too. A decoded map keeps the order its keys arrived in: Python's `dict` and Ruby's `Hash` keep insertion order, and TypeScript remembers the arrival order of each map it decodes beside the plain object. Python and Ruby sort a state's dots in UTF-16 code unit order when they build its signed view. Since v0.1.31 the schema layer also holds the capability pipe records of annex I. Python's `aggregate`, `semantic`, and `ordered` capabilities read them through `records.py`; TypeScript's `capabilities/aggregate.ts` and `capabilities/semantic.ts` through `records.ts`, `@agentspaces/ordered` in `packages/ordered/src/raft.ts`, and `@agentspaces/webrtc` in `packages/webrtc/src/signal.ts`; and Ruby's aggregate, semantic, and ordered clients through `schema.rb`. A client's `double` field takes any float64, as Java's does, and `TakeClaim` keeps its own finite-bid check. Each client refuses a bignum past 1000 bytes in its decoder and its encoder, a stamp past 3996 UTF-16 units, and a clock node past 3965, and TypeScript's `cbor.dumps` writes a `Map` with text keys as a map in insertion order. Each client runs the vectors of SPEC annex I from its own copy (Python's `tests/wire_encoding_vectors.json`, TypeScript's `test/wire-encoding-vectors.json`, and Ruby's `test/wire-encoding-vectors.json`, each byte-identical to the core file, Ruby's since v0.1.31) in `tests/test_wire_encoding_round_six.py`, `test/wire-encoding.test.ts`, and `test/wire_encoding_test.rb`, and the round-seven vectors and pipe records in `tests/test_hlc_round_seven.py`, `test/hlc-round-seven.test.ts` with `packages/webrtc/test/signal.test.ts`, and `test/hlc_round_seven_test.rb`.

### 1.2 Cryptographic primitives

Signatures are Ed25519 (RFC 8032) via the JDK provider; raw public keys are 32 bytes. Hashes are SHA-256. Content identifiers and self-certifying ids use multibase base58btc encoding (a leading `z` character followed by the base58btc alphabet). Symmetric encryption is AES-256-GCM with 96-bit random nonces and 128-bit tags. Key agreement for key distribution is X25519 (RFC 7748) with HKDF-HMAC-SHA-256 (RFC 5869).

### 1.3 Identifiers

| Identifier | Derivation | Serialized form |
| --- | --- | --- |
| `PeerId` | `multibase(sha-256(raw Ed25519 public key))` | the multibase string |
| `AgentId` | a `PeerId` plus a local name; under a subordinate identity (SPEC §4.2) the name is further bound to an agent key by a peer-signed `AgentCertificate` (§4, §7.2) | `<peerId>/<localName>` |
| `GroupId` | `multibase(sha-256(canonical CBOR of the founding document))`, where the founding document is `FoundingDocument{fields, signature}`: the advertisement's founding fields `(name, founder, issued, ttl, membershipPolicy, defaultStrategy, gossip)` and the founder's Ed25519 signature over their canonical CBOR (`GroupFounding`) | the multibase string |
| `SpaceId` | `multibase(sha-256(canonical CBOR of the founding SpaceAdvertisement))` for an advertised space; `multibase(sha-256("local:" + name))` for a purely local space (`SpaceId.fromFounding`, `SpaceId.local`) | the multibase string |
| `EntryId` | issuer-generated UUID | the UUID string |

GroupIds and SpaceIds are self-certifying: possession of the founding document's bytes proves the name, because the name is the hash of those bytes, and a receiver that re-derives the id from a document it was handed detects a substituted policy. The URI forms `aspace://<groupId>` and `aspace://<groupId>/<spaceName>` are the advertisements' `id` fields (SPEC §4.4), and `GroupFounding.verify` checks that the group advertisement's `id` URI names the derived group.

### 1.4 Hybrid logical clock

Every item on the wire is stamped by a hybrid logical clock (Kulkarni et al.). A timestamp is `(physical, logical, node)`: epoch milliseconds, a logical counter disambiguating events within one millisecond, and the issuing node's id. The canonical serialized form is the string `physical:logical:node`. Ordering is total: physical, then logical, then node by UTF-16 code units (`String.compareTo`), which is what makes `LEASE_RACE` arbitration (§7.6) deterministic fleet-wide. The clients compare node parts and claim holders by UTF-16 code units too, since an order by code point differs once a character above U+FFFF meets one from U+E000 to U+FFFF (SPEC §9; v0.1.30).

The clock (`HybridLogicalClock`) issues a local stamp (`now()`) at `physical = max(wall, lastPhysical)`, with `logical = lastLogical + 1` when the physical part did not advance and 0 when it did. A merge (`update(remote)`) takes the largest of wall time, `lastPhysical`, and the clamped remote physical part, then advances the logical counter of whichever of the last and the remote stamps hold that maximum (the larger counter when both do), or starts at 0 when wall time alone holds it. These hardening rules govern the clock (SPEC §9; all but the drift cap since SPEC v0.1.30, and the drift cap's clamp moved one millisecond inside the ceiling in the same revision):

- *The acceptable stamp.* `HlcTimestamp.parse` decodes only the canonical stamp grammar of SPEC §9 (v0.1.30): the physical and logical parts are each `0` or a non-zero ASCII digit followed by ASCII digits, with no leading zero, sign, fraction, exponent, whitespace, or non-ASCII digit; the physical part fits `long` (at most 9223372036854775807) and the logical part fits `int`; the node is non-empty and holds no `:`, no control character (U+0000 to U+001F, U+007F), and no lone surrogate (SPEC v0.1.30, E11). The `HlcTimestamp` constructor refuses the same nodes and a negative part, so no constructed stamp encodes to text `parse` refuses, and every stamp Java holds re-encodes to exactly the text its signer signed. `HybridLogicalClock.isAcceptable(stamp)` then requires `logical <= LOGICAL_LIMIT`. `parse` keeps an otherwise canonical counter above the limit, so the merge point can verify the signature over it first and strike the signer it names. Java decodes every stamp in a frame or a space delta before it verifies the signature that covers it, so a stamp that does not parse makes its carrier undecodable: `WireCodec.decode` refuses the frame, counts it in `PeerNode.framesDropped()`, and strikes nobody, and a space delta or sync delta that carries one fails to decode in `ReplicatedSpace`, drops whole, and counts in `ReplicatedSpace.deltasUndecodable()`. An inner frame of a verified `BATCH` that does not decode counts in `framesDropped()` too, and `PeerNode` strikes the outer signer, whose signature covers the inner bytes, with `malformed frame in BATCH`. That strike is the one exception to striking nobody for an undecodable carrier (SPEC §9), and no client handles `BATCH` (SPEC v0.1.30, E15). The Python, TypeScript, and Ruby clients parse every stamp with the same grammar wherever they decode, merge, order, or deduplicate by stamp, the `signedAt` of an agent-signed state included, and decode a counter up to 2147483647, so the merge point refuses one above the limit after verification as Java does; TypeScript holds the physical part to the full signed 64-bit range, and Ruby refuses a byte string in a stamp's place. A client drops a space delta whose stamps do not all decode whole, before any signature check, and counts it in its `deltasUndecodable` count (Python `deltas_undecodable`, Ruby `deltas_undecodable`); a frame whose stamp does not decode drops at the client's frame decoder, before any signature check, and counts with its other undecodable frames (Python `Peer.malformed_frames`, TypeScript `Peer.malformedFrames`, Ruby `Peer#malformed_frames`) (SPEC v0.1.30, D5, E9). TypeScript's `FrameFilter` also keeps `framesUndecodable` for an envelope a caller hands it directly, which a frame the peer decoded never is. The Rust peer has not yet adopted the grammar (§11).
- *The stamp item (SPEC v0.1.30, D3, E1).* A stamp decodes only from a definite-length, untagged CBOR text string under its shortest length header and in shortest-form UTF-8 (SPEC §9). Jackson's CBOR parser decodes overlong UTF-8, drops tags, joins indefinite-length chunks, and reads a longer length header without a trace, and a frame's signature verifies over the re-encoded envelope, so a repaired item once passed as signed. `CborCodec` therefore registers `CanonicalStamps`, which decodes every `HlcTimestamp`: it refuses a token that is no text string and a text string under a tag, re-encodes the decoded text as the shortest-form item (`CanonicalStamps.textItem`), and requires the bytes the item occupies in the input, which `CborCodec.fromBytes` passes as a context attribute, to equal it. The deserializer also refuses a stamp it would decode from buffered tokens, which no longer show their bytes. Every refusal makes the carrier undecodable, with the counts above. The clients judge the raw item too: since round six their decoders refuse any head longer than its argument needs and any indefinite-length text of 3996 UTF-16 units or fewer (SPEC §9.1, S3 and S6), so no such item reaches a stamp parser. Java, Python, TypeScript, and Ruby therefore refuse such items, which the Rust peer still accepts (§11). Since v0.1.31 a stamp holds at most 3996 UTF-16 units (`HlcTimestamp.MAX_STAMP_UNITS` in Java, which the constructor enforces, `MAX_STAMP_UNITS` in Python and TypeScript, and `HLC_MAX_STAMP_UNITS` in Ruby), because a longer text can travel only in Jackson's chunks. Every implementation refuses such a text as a stamp, and every ref reader falls back from a `pdt.issued` that holds one.
- *CBOR outside a stamp (SPEC v0.1.30, E8; v0.1.31).* `CborCodec.fromWire` and `fromDocument` run `WellFormedCbor.checkCanonical` over the raw bytes before Jackson reads them (§1.1), so every implementation decodes the rest of a frame or a space delta under the item rules of SPEC §9.1. An indefinite-length text string stands only for a text past 3996 UTF-16 code units, in Jackson's exact chunks; tags 2 and 3 stand only for an integer outside the `long` range and tag 4 only for a normalized decimal, and none stands in a protocol field or a map key's place; every text, map keys and chunks included, is well-formed shortest-form UTF-8. Each client decoder applies the same rules, reads tag 2's bytes as the magnitude and tag 3's as the magnitude negated, and writes a text over 3996 UTF-16 units in Jackson's chunks, so a signature over Java's long strings verifies in each. The protocol's one other tag, 42, links persistent-tree nodes and decodes only in `NodeCodec` and the clients' node codecs, which read node bytes that travel as byte strings. Every implementation refuses an indefinite-length byte string (SPEC §9.2, R12). Round five accepted tags 2 and 3 over any byte string and tag 4 with any exponent in an `int`, and read the exponent -2^31 through Java's wrapped negation; rule S9 refuses all three, and rule S6 refuses a short text in chunks, so the vectors `C2 41 80`, `C3 41 FF`, `C4 82 3A 7F FF FF FF 01`, and `7F 63 61 62 63 63 64 65 66 FF`, which earlier text accepted, now drop.
- *The local node (SPEC v0.1.30, D6, E11 and E17).* The `HybridLogicalClock` constructor throws `IllegalArgumentException` for a node that `HlcTimestamp.canonicalNode` refuses (empty, or holding `:`, a control character, or a lone surrogate, a UTF-16 surrogate without its pair), so a peer never emits a stamp whose node breaks the grammar. The clients keep one clock state per node behind `hlc_now` (Python, Ruby) and `hlcNow` (TypeScript, through `clockOf`), and each refuses a node the grammar refuses there, before every stamp it issues for that node: Python raises `ValueError`, TypeScript throws, and Ruby raises `ArgumentError`, and Ruby's `Identity#agent` also refuses such an agent name when it builds the agent id. Since v0.1.31 each clock also refuses a node past 3965 UTF-16 units (`HlcTimestamp.MAX_NODE_UNITS` in Java, `MAX_NODE_UNITS` in Python and TypeScript, `HLC_MAX_NODE_UNITS` in Ruby), which is 3996 less the longest physical and logical parts and their two colons, so every stamp it issues fits in one definite text. SPEC §9 names these places.
- *The advisory head stamp (SPEC v0.1.30, D2, E10; v0.1.31, rules R1 to R3 of SPEC §9.2).* `Refs.toHead` orders a head by the reserved `pdt.issued` attribute only when it is text that `HlcTimestamp.parse` accepts, `isAcceptable` holds, its physical part lies at most `MAX_DRIFT_MILLIS` plus the 5,000 ms skew margin past the reader's wall time (R2), and `pdt.issuer` is absent or text that passes `AgentId.parse`; it pairs `pdt.issued` with `pdt.issuer`, or with the entry's own issuer when `pdt.issuer` is absent. Otherwise, a null or non-text value included, it orders the head by the entry's own `issued` stamp and issuer together, and it refuses, counts, strikes, and drops nothing for the pair. `PRef.attrs` holds text under every other key: a null or any other item there makes the ref undecodable (R1), and `Refs` counts such an entry, with an entry whose head breaks a bound or names another kind or ref, once in `headsIgnored()` while the entry stays live (R3), learning of the undecodable ones through `Space.undecodableEntries`. The Python (`pdt.refs`, `heads_ignored`), TypeScript (`pdt/refs.ts`, `headsIgnored`), and Ruby (`pdt/refs.rb`, `heads_ignored`, reported as `headsIgnored`) ref readers apply the same rules.
- *The drift cap.* A merge clamps the remote physical component to local wall time plus `MAX_DRIFT_MILLIS` (600,000 ms) minus one millisecond, so a peer forging a far-future stamp cannot poison the clock and make its own later stamps sort after all honest ones. The clamp sits one millisecond inside the ceiling so that the carry holds the ceiling too: at wall time `W`, `update((W + 600000, 65536))` clamps the remote part to `W + 599999`, carries, and returns `(W + 600000, 0)`, which a receiver's far-future check (§3 step 6) accepts. The ceiling holds for up to 65,536 clock events, `now()` and `update` calls alike, per millisecond of wall time; each further event in the same millisecond carries one millisecond past it, and the skew margin of §3 step 6 keeps such a frame from a strike.
- *The logical limit.* `LOGICAL_LIMIT` is 65,536 (2^16). Every merge point refuses a remote stamp that is not acceptable before the stamp reaches the clock, counts the refusal, strikes the signer wherever a verified signature names one, and ignores the frame (§3), the folded state (§7.5; its `issued`, `leaseStamp`, and `signedAt`, the last since SPEC v0.1.30, D1), or the claim (§7.6) that carries it. A stamp at exactly `LOGICAL_LIMIT` merges. `update` throws `IllegalArgumentException` for an unacceptable stamp and leaves the clock unchanged, so a merge point that skipped the check fails loudly.
- *The carry.* An increment, local or in a merge, that would take the counter past `LOGICAL_LIMIT` advances the physical part by one millisecond and resets the counter to 0. The clock therefore never returns the same stamp twice and never issues a counter above `LOGICAL_LIMIT`, whatever it merges.

Before v0.1.30 the clock adopted a remote counter unchecked and saturated it at `Integer.MAX_VALUE`. One signed stamp with a physical part just inside the drift cap and the counter at `Integer.MAX_VALUE` then made `now()` return the same `(physical, MAX, node)` until wall time passed that physical part, up to ten minutes, and a repeated stamp kept it there. The replay filter of §3 dropped every later frame of the frozen node, so failure detectors evicted it; a frozen replica's lease renewals tied with the leases they renewed, and `LwwRegister.merge` keeps the held value on a tie, so leases stopped extending, lapsed, and let taken entries reappear; and the claim lattice of §7.6, which prefers the lower stamp, made a replica stamping ten minutes ahead lose every contested take. Because record, lease, and claim stamps travel inside replicated entries, one hostile entry froze every replica that gossip and anti-entropy brought it to. An honest counter resets every millisecond and stays tiny, and the carry keeps it within the limit under any load, so the refusal never meets a stamp from a conforming peer.

### 1.5 Cross-language conformance

The wire format is proven language-independent by golden vectors (`agentspaces-spec/golden.json`, the source beside this document, vendored into each implementation: `agentspaces/tools/golden/golden.json`, `agentspaces-python/tests/golden.json`, `agentspaces-typescript/test/golden.json`): a fixed private key, and the byte-exact expected values for the derived peer id, group id, HLC encoding, a PING body, envelope, signature, and full frame, a peer advertisement plain and signed, and rumor bodies. The Python and TypeScript clients reproduce every vector byte-identically and interoperate with Java peers live. The subordinate-key vectors (v0.1.11) are `agent_private_key_pkcs8`, `agent_public_key_raw`, `agent_certificate_unsigned_cbor`, `agent_certificate_signature`, `agent_certificate_cbor`, `record_signature_agent_key`, `entry_state_with_certificate_cbor`, and `delta_with_certificate_cbor`, verified against the receiver clock `certificate_verify_at` (the golden record's own issue instant, so a replica pinned there holds the record's lease live and the certificate inside its window at once), plus five hostile deltas every implementation must drop: `adv_cert_wrong_peer_delta`, `adv_cert_wrong_agent_delta`, `adv_cert_expired_delta`, `adv_cert_uncertified_key_delta`, and `adv_cert_peer_signed_record_delta`. Phase 3 adds `agent_card_with_key_cbor`/`_signature`, `take_claim_agent_signature`, `claim_delta_with_certificate_cbor`, and three hostile claim proofs (`adv_claim_cert_peer_signed_delta`, `_expired_`, `_wrong_holder_`). v0.1.14 adds `join_ticket_record_cbor`, the reserved `JoinTicket` entry a fan-in writes in its fleet-wide modes, so a client recognises the type and never acts on it. `SignedAgentVectorsClusterTest` gossips those bytes into a real replica; the clients fold them through their own `Peer`. §10 gives the checklist a new client implements.

## 2. Why These Protocols

A reader meeting the protocol inventory for the first time can reasonably ask why one system runs SWIM, gossip, CRDTs, a claim lattice, an auction, Raft, and push-sum side by side. The inventory looks eclectic; the selection rule behind it is single and strict. Distributed systems offers no protocol that is simultaneously cheap, always available, and strongly consistent, so every guarantee has a price, and the design principle the whole suite follows (SPEC §2, P1: the weakest sufficient primitive) is to buy each guarantee only where its question demands it. Each protocol below answers exactly one question, at the lowest cost the literature knows for that question, and the questions are different enough that no one protocol answers them all well. A fleet built on a single stronger protocol, say consensus for everything, would answer every question correctly and pay quorum latency and quorum liveness on every membership change, every cache refresh, and every task grab; a fleet built on a single weaker one, say gossip for everything, would be fast everywhere and unable to promise exactly-once anywhere.

The map from question to protocol:

| The question | The protocol | What it costs | Why nothing weaker or stronger |
| --- | --- | --- | --- |
| Who is alive right now? | SWIM (§5.2) | one probe per node per tick, O(1) regardless of fleet size | all-to-all heartbeats cost O(N²) messages; consensus-managed membership makes liveness itself depend on a quorum, so the failure detector fails exactly when it matters |
| How does everyone learn X? | epidemic gossip, rumor channel (§5.3) | O(log N) rounds, fanout messages per node | a broker is a deployment and a partition point; a full mesh is N² connections; flooding is exponential traffic |
| How is learning X guaranteed? | anti-entropy digests (§5.4) | one digest exchange per node per tick | rumors alone can miss a peer that was down; periodic pairwise reconciliation makes convergence certain, cheaply |
| How does shared state stay writable through partitions? | delta CRDTs (§7.3) | metadata per entry (dots, stamps); no write-path coordination at all | anything coordination-based blocks writes on the minority side of a partition, which forfeits local-first operation (P7) |
| Who gets this task? | the claim lattice under LEASE_RACE (§7.6, §7.7) | one settle window of latency | exclusivity is the one thing CRDTs cannot express, and full consensus per take is overkill when the monotone completed flag already guarantees at most one completion; transient duplicate work is the accepted price, and idempotent tasks make it a non-event |
| Who should get this task? | CBAA/CBBA auction rounds (§7.7) | a few gossip rounds to converge | cost-aware allocation is an optimization problem across bidders; a central auctioneer reintroduces the hub, and plain LEASE_RACE ignores cost entirely |
| What exact order did decisions happen in? | Raft ordered log (§8.3) | majority quorum for liveness, a log round-trip per decision | nothing weaker gives exactly-once; this is the one genuinely consensus-shaped question, so consensus runs here and only here, opt-in per space (P1) |
| What is the fleet-wide total or average? | push-sum (§8.2) | O(log N) rounds of small pipe frames | a collector node is a hub and a hotspot; consensus on an aggregate is absurdly overpriced for an approximate, converging figure |
| What happened before what? | hybrid logical clocks (§1.4) | 64+32 bits and a node id per stamp | synchronized wall clocks do not exist in practice; vector clocks grow with fleet size; HLC gives a total order close to wall time in constant space |

Two mechanisms tie the selections into one system rather than a grab bag. The first is the lease (P2): SWIM membership, cached advertisements, space entries, take claims, and subscriptions all expire unless renewed, so every protocol above shares a single failure idiom, the absence of renewal, and no pairwise failure-handling matrix exists between them. The second is layering by escalation: gossip and CRDTs are the default floor everything runs on; the claim lattice adds arbitration only on `take`; the auction adds economics only on AUCTION spaces; Raft adds total order only on ORDERED spaces. An application escalates a space one rung when its workload proves it must, and pays that rung's price for that space alone.

None of these protocols is invented here, deliberately. SWIM is Das, Gupta, and Motivala (2002); epidemic dissemination and anti-entropy are Demers et al. (1987); push-sum is Kempe, Dobra, and Gehrke (2003); CRDTs are Shapiro, Preguiça, Baquero, and Zawirski (2011); hybrid logical clocks are Kulkarni et al. (2014); Raft is Ongaro and Ousterhout (2014); the auction-consensus family is Choi, Brunet, and How's CBAA/CBBA (2009). The contribution of AgentSpaces is the composition: one identity layer under all of them, one lease semantic across all of them, and one selection rule deciding which of them answers which question.

## 3. The Frame

Every frame between peers, over every transport, is the CBOR of a signed wrapper:

```
Signed {
  envelope        : Envelope
  senderPublicKey : bytes | null (32, raw Ed25519; null on a channel-attested frame)
  signature       : bytes | null (Ed25519 over the envelope's canonical CBOR; null likewise)
}

Envelope {
  ver   : int            (WireCodec.WIRE_VERSION = 3; the only version receivers accept)
  group : GroupId
  kind  : Kind           (enum, §3.1)
  from  : PeerId
  to    : PeerId | null  (the intended recipient; null only on an unaddressed bootstrap introduction)
  stamp : HlcTimestamp
  body  : bytes          (kind-specific CBOR, §3.1)
}
```

A receiver (`WireCodec.decode`) accepts a frame only when all of the following hold: the frame decodes through `CborCodec.fromWire` (§1.1), so it is one item in the wire encoding, its wrapper and envelope hold exactly their fields in declared order with each field's own kind, and their encoding equals the bytes received, its envelope stamp included (`HlcTimestamp.parse` over the canonical stamp item, §1.4); `envelope.ver` equals 3, checked before any signature work, so a frame of another version costs no verification and is counted in `PeerNode.framesDropped()` without striking its sender; the wrapper carries both the sender key and the signature, or both null; when both are present, the sender key is 32 bytes, `sha-256(senderPublicKey)` multibase-encodes to exactly `envelope.from` (the self-certifying check), and the signature verifies over the envelope's canonical CBOR; when both are null, the connection's `attestedPeer()` equals `envelope.from` (SPEC §5.6). A frame failing any check is dropped before any handler sees it. The dispatcher (`PeerNode.dispatch`) then judges the frame in this order (SPEC §9; the stamp bounds since v0.1.30):

1. It drops frames for groups this peer has not joined, frames from revoked or locally quarantined peers, and frames whose `to` names another peer (the destination binding).
2. It drops stale frames and exact replays (`isStaleOrReplay`). A frame whose stamp's physical part trails the receiver's wall time (`clock.millis()`, the node's injected `InstantSource`) by more than `MAX_FRAME_AGE_MILLIS` (300,000 ms) counts in `framesStale`; a repeat of a `(from, stamp)` pair among the last 8,192 frames (`RECENT_FRAMES_CAPACITY`, evicted in insertion order) counts in `framesReplayed`. Neither drop strikes the sender, because anyone can replay a frame its author signed; every later check judges a fresh frame that only its signer could have produced, so its strikes are attributable.
3. It applies the required-attestation check when configured (§5.2).
4. It hands a frame from a peer that is not yet a member to the bootstrap path, under the bootstrap rate budget, which answers `PING`, `CHANNEL_HELLO`, and `GROUP_AD_WANT` (§3.1) and accepts a self-introduction on the `peers` stream. The bootstrap path refuses an introduction whose stamp is not acceptable (§1.4) before admission: it drops the frame, counts the refusal, and strikes the sender with the reason `logical counter above 65536`, so a hostile introduction admits nobody, even in an `OPEN` group. An introduction that admits the newcomer merges its stamp into the local clock. It drops every other non-member frame before any side effect.
5. For a member's frame, it applies a per-issuer token bucket (capacity 50,000 frames, refill 10,000 per second, monotonic nanotime accounting behind an injectable nanosecond source so the bound is testable deterministically), which bounds what any single admitted peer can make the node process, and strikes a sender that overdraws it.
6. It judges the stamp against the receiver's wall time (`clock.millis()`). A stamp whose physical part is strictly greater than wall time plus `MAX_DRIFT_MILLIS` drops the frame. With the skew margin of 5,000 ms (SPEC §9; v0.1.30), `PeerNode` counts a stamp at most that margin past the ceiling (`FAR_FUTURE_SKEW_MARGIN_MILLIS`) in `framesFarFutureSkewed()` and strikes nobody, and counts a stamp further past it in `framesFarFuture()` and strikes the sender with `far-future stamp`. A stamp that is not acceptable (`HybridLogicalClock.isAcceptable` false) drops the frame, counts in `PeerNode.framesLogicalRefused()`, and strikes the sender with `logical counter above 65536`. Neither stamp reaches the clock. An honest sender a hostile stamp dragged to the cap keeps its stamps at or below its own wall time plus `MAX_DRIFT_MILLIS` (the clamp and carry of §1.4). A receiver whose wall clock trails the sender's by up to the skew margin drops and counts those of its frames that land past the receiver's own ceiling and strikes nobody, so the honest sender never accumulates strikes toward quarantine; strikes never decay, and without the margin a few milliseconds of skew struck it on every frame. The stamp checks run in the order SPEC §9 fixes: the parse at decoding, the stale and replay checks of step 2, then the far-future and acceptable-stamp checks of this step; each client's frame filter applies the same order.
7. It merges the envelope stamp into the local clock, caches the connection, and records the sender as heard for membership.

## 4. Layer 0: Identity and the Signature Inventory

A peer generates an Ed25519 keypair on first start; `FileKeystore` persists it, and the derived `PeerId` therefore survives restarts, addresses, and transports. The private key never leaves the `PeerIdentity` object; every other component asks it to sign.

Nine distinct signatures exist in the system. This inventory is the map an auditor wants:

| What is signed | Canonical bytes | Signer | Verified by |
| --- | --- | --- | --- |
| Wire frame | the envelope's CBOR | sending peer | every receiver, before dispatch (§3); elided on attested channels (SPEC §5.6) |
| Advertisement | the advertisement record's CBOR | issuing peer | every receiver, before caching (§6.2); the multicast beacon's `SignedPeerAd` carries this same signature outside any envelope (§5.1) |
| Founding document | `FoundingFields` = `(name, founder, issued, ttl, membershipPolicy, defaultStrategy, gossip)` | the group founder | `joinGroup` and every `GROUP_AD` receiver, together with re-deriving the GroupId (§1.3, §5.2) |
| Entry record | `SignView` (§7.2), the record's immutable identity | writing peer, or the writer's certified agent key under a subordinate identity | every replica, before merging a delta (§7.2's two-key rule) |
| Agent certificate | `AgentCertificate` minus `peerSignature` = `(agent, agentPublicKey, issued, ttl, encryptionPublicKey?)`, the X25519 key appended in v0.1.13 and omitted when absent | the agent's peer | every replica receiving a record under that agent's key, before verifying the record (§7.2); `AgentCertificates.verify` |
| Entry state transition | `StateSignView` (§7.4), the mutable CRDT fields | issuer, or take-claim holder for a completion; that party's own agent key when it is attested (v0.1.13) | every replica, before merging a delta |
| Take claim | the claim record's CBOR | claiming peer, or the holder's certified agent key under a subordinate identity (the peer key still rides as `holderKey`) | every replica, before merging the claim (§7.6's two-key rule) |
| Join credential | `CredentialView` = `(candidate PeerId, GroupId)` | a group founder | admission (§5.2) |
| Content-key epoch (v0.1.13) | `EpochCommitment` = `(group, epoch, cutover, keyDigest)`, `keyDigest` the SHA-256 of the epoch key | the rotator (the founder or a `KEY_ROTATE` grantee), carried as `EpochProof(rotatorKey, signature)` | every member, before installing an epoch key from a key-wrap response (§8.7, SPEC §11a.3) |

Every verification resolves the signer's key the same way: the raw public key travels beside the signature, and the receiver checks that the key hashes to the self-certifying id it must belong to (the envelope's `from`, the advertisement's `issuer`, the record's issuing peer, the claim's holder, the group's founding issuer). No key registry exists anywhere in the system. The one indirection is the agent certificate (SPEC §4.2): the peer key still travels beside the record and hashes to the record's issuing peer, and the certificate that key signs carries the agent key the record signature is then checked under.

**The authorizer and its enforcement points (SPEC §11, v0.1.11).** Identity says who a peer is; the `Authorizer` SPI (`agentspaces-api`, `permits(PeerId, Operation, String scope)`) says what it may do, and every privileged operation in the reference implementation asks it. Two implementations ship. `MembershipAuthorizer` permits an admitted member of the group for every operation unless a grant set for that operation is configured, in which case only the listed PeerIds are permitted. `OidcAuthorizer` validates an identity-provider JWT with Nimbus against a configured issuer, audience, and JWKS URL, requires the `agentspaces_peer` claim to name the peer being judged, reads the permitted operations from the space-delimited `scope` claim (`aspace:<operation>` for every scope of the operation, `aspace:<operation>:<scope>` for one, the operation name in lower case with a hyphen, as in `aspace:space-write:tasks`), caches the grant until `exp`, and receives tokens through `authorize(peer, token)` from the credential-hint listener of §5.2. The JWT's signature is the identity provider's and is verified against its JWKS; it sits outside the Ed25519 inventory above. Every enforcement point keeps a membership-rooted construction path beside the authorizer one:

| Operation | Scope | Enforcement point | Seam |
| --- | --- | --- | --- |
| `RAFT_VOTER` | group id | `RaftLog` (§8.3): an inbound frame needs membership in the fixed member set and `permits(from, RAFT_VOTER, group)`; a `clientSubmit` from a member the authorizer refuses is dropped | constructor taking `Authorizer` and `GroupId` (the log never held the group id itself); the member-list constructor permits exactly the members |

| `KEY_HOLDER` | group id | `GroupKeyDistributor` (§8.7): the verified requester must be permitted; an agent asking for itself is asked per agent (`permits(AgentId, …)`, v0.1.13) | `serve(key\|ring, Authorizer, GroupId)`; `serve(key, membership)` stays as the default; `agentsAllowed(Predicate)` overrides |
| `KEY_ROTATE` | group id | `GroupKeyDistributor.rotate` and every member's install of an epoch key (v0.1.13): the founder or a permitted peer; the `MembershipAuthorizer` grants it to nobody unless `grants.key-rotator` names the peer | `serve(ring, Authorizer, GroupId)`; `rotators(Predicate)` overrides |

| `VOTE` | vote space name | `VoteCapability` (§8): `tally` counts a ballot only from a permitted issuer, asked per agent (`permits(AgentId, …)`), at the authorizer's `granularity(VOTE, space)` — one counted ballot per peer under `PEER`, one per attested granted agent under `AGENT` — alongside the electorate predicate, and `castBallot` refuses to write a ballot this agent is not permitted to cast | constructor taking `Predicate<AgentId>` and `Authorizer`; the earlier constructors permit every issuer, so the electorate decides alone |
| `MODEL_SERVE` | model name | `FleetChatModel` (`agentspaces-springai`, v0.1.12) accepts a `ModelResponse` or `ModelChunk` only when its space-authenticated issuer is permitted for the answering model; the model-server auto-configuration asks about its own peer per served model and logs a warning when refused | `FleetChatModel` constructor taking `Authorizer` |

Under Spring Boot the `Authorizers` bean selects by `agentspaces.security.profile`: `DEV_LOCAL` and `MTLS` build one `MembershipAuthorizer` per networked group with grants from `agentspaces.security.grants.{raft-voter, directive-issuer, connector-serve, key-holder, key-rotator, space-write, space-take, vote, model-serve}` (PeerId lists; empty permits any admitted member, except `key-rotator`, where empty leaves rotation to the founder alone); `MTLS_OIDC` and `ZERO_TRUST` build one `OidcAuthorizer` from `agentspaces.security.oidc.{issuer, audience, jwks-url}` and fail fast, naming the property, when any is missing, ignoring the grants. The `Authorizer` bean is the group's instance with one membership-rooted group and a union ("permitted by any configured group") with several; `Authorizers.forGroup(name)` gives per-group access. A `DirectiveGates` bean offers `attach(space, worker)` with the profile's authorizer and the group id as scope. When command and control is enabled, the `DIRECTIVE_ISSUER` grant becomes the configured issuers plus this node, so worker nodes list the console PeerId under `grants.directive-issuer`. `RaftLog` and `DataQueryClient` are not auto-wired; an application passes the bean to them. The node's own token, from `agentspaces.security.oidc.token` or `token-file` (re-read every card-refresh tick), is placed in the `aspace:oidc` hint and self-authorized; a token that fails validation at startup logs a warning, since the identity provider may be briefly unreachable.

## 5. Layer 1: Peering

### 5.1 The tick

Progress is tick-driven. Each `PeerNode.tick()` runs, per joined group: republish the peer's leased self-advertisement on the membership stream, run one SWIM probe round, and, once the group's gossip `period` has elapsed on the node's clock since the last round (the first round runs immediately after the join), run one anti-entropy round with one random partner. `startTicking(period)` runs this on a timer; the examples and tests tick every 250 ms, so with the default one-second gossip period every fourth tick reconciles. When the multicast beacon is enabled (§5.2), the tick also sends the beacon datagram once its interval has elapsed. Everything else (rumor forwarding, frame handling) happens inline as frames arrive. A test that drives a frozen clock must advance it between ticks, or anti-entropy never runs again after the first round.

### 5.2 Membership: SWIM and admission

Membership (`GroupMembership`) is leased SWIM. Configuration is `(memberTtl, pingTimeout, indirectPeers)` with defaults 30 s, 2 s, and 2. Each probe round pings one random member with a nonce; an unanswered ping after `pingTimeout` triggers `PING_REQ` to `indirectPeers` other members, who probe the target on the asker's behalf and relay the `ACK` with the target named in `onBehalf`. A member unanswered through the indirect stage is marked suspect, a local flag that no frame disseminates; any frame heard from a member clears suspicion and refreshes its lease; a member silent past `memberTtl` drops from the view without ceremony. The view feeds `PeerSampler.randomMembers(n)`, the primitive every gossip channel and capability draws partners from.

Peers introduce themselves on the reserved rumor stream `peers`, whose items are signed peer advertisements with the default hop budget. Admission enforces the group's membership policy at this ingestion point: an `OPEN` group admits every verified peer advertisement; an `INVITE` group requires the candidate's advertisement to carry, in its resource hints under the key `aspace:join`, a base64 credential whose CBOR decodes to a founder key and a founder signature over `(candidate PeerId, GroupId)`, with the founder key hashing to the group's founding issuer; a `POLICY` group delegates to the `MembershipValidator` SPI. A peer that fails admission is never entered into membership, so it can gossip nothing further into the group.

*Credential hints.* The same resource-hint map carries the OIDC token of SPEC §11. A node places its token under `JoinCredentials.OIDC_HINT_KEY` (`aspace:oidc`) with `PeerNode.credentialHint(key, value)` and withdraws it with `removeCredentialHint(key)`; node-level hints merge under the per-group join hints, and the group hint wins on a key clash. A `CredentialHintListener`, registered with `PeerNode.Builder.onCredentialHints(listener)` or the instance method `onCredentialHints` (the starter attaches it after the node bean exists), receives `(peer, hints)` on a member's first admission and whenever that member's hint map changes, deduplicated against the last map seen per peer in an LRU of 4,096 peers. The starter's listener hands the `aspace:oidc` value to `OidcAuthorizer.authorize(peer, token)`. A token of under 2 KiB rides the self-advertisement every gossip period, and because the token's `agentspaces_peer` claim names one PeerId, a hint copied from one advertisement into another grants nothing.

*Joining.* `PeerNode.joinGroup(SignedGroupAdvertisement, …)` refuses, with an `IllegalArgumentException`, a founding advertisement that fails `GroupFounding.verify` (§1.3, §4), and members joined this way answer `GROUP_AD_WANT` with the document they joined with. `joinGroup(GroupId, config, seeds, timeout)` implements SPEC §10.1's `join: aspace://…`: it sends `GROUP_AD_WANT` to each seed, accepts the first `GROUP_AD` whose document verifies and derives to exactly that GroupId, ignores every other answer, joins with the accepted document, and throws `TimeoutException` when no seed served one in time. While it waits it works in slices of 1 s, 2 s, 4 s, then 5 s each up to the timeout: at each slice it dials again every endpoint that is not connected, sends `GROUP_AD_WANT` again on every connection it holds, and asks its locator again (on its own thread, so a slow locator never extends the timeout) while nothing is connected; the timeout's report names the locates, the endpoints dialed and connected, and the last hint. The older `joinGroup(GroupAdvertisement, …)` with a literal id remains for local configuration; a node never serves such a group to newcomers.

*Required attestation.* With `PeerNode.Builder.requireAttestation(true)`, the enterprise-CA posture, every inbound frame must arrive on a connection whose `attestedPeer()` equals `envelope.from`, admission frames included: a bootstrap introduction needs an attested channel, and a peer advertisement forwarded by a third party refreshes existing members only. Frames on unattested connections, or on connections attested for someone else, are logged and dropped; relayed inner frames are dropped in this mode; the check runs after the replay deduplication of §3. A signed frame from a current member arriving on a connection that attests nobody means that connection's fresh handshake attested nothing (a revoked, expired, or replaced certificate): the node evicts the member, closes the cached connection, and refuses the member at dispatch until one of its frames arrives attested again. A frame attested for a different peer is dropped and never evicts. `TlsTcpTransport.withRefreshableTrust(identity, serving, Supplier<ChannelTrust>)` lets a deployment swap in new CRLs without a restart. A CA-rooted `RevocationValidator` that would let the gossiped revocation advertisement carry a CA verdict is not implemented, because nothing maps a PeerID to its certificate.

*Multicast beacon.* `PeerNode.Builder.multicast(group, interval)` enables the opt-in LAN beacon (`MulticastBeacon`). Each interval on the node's clock, the node sends one UDP datagram per joined group to the multicast group with IP TTL 1: the CBOR of `SignedPeerAd{adBytes, publicKey, signature}`, the node's own signed self-advertisement with no envelope and no frame kind, at most 65,507 bytes. A receiver charges the datagram to its bootstrap token bucket, verifies key-hashes-to-issuer, the signature, an unexpired advertisement, and an issue time within ten minutes of local time, requires the named group to be one it has joined, applies the group's admission policy, and then introduces itself to the advertised endpoints as if they were configured seeds. Under required attestation the datagram admits nobody and serves only as a seed hint. The in-repository tests drive the beacon through an in-memory `Datagrams` carrier; the real UDP carrier is exercised only by hand, because loopback multicast has no route on the macOS CI hosts.

### 5.3 Gossip: the rumor channel

The rumor channel (`GossipBus`) pushes new items on named streams. Publishing marks the item seen locally and sends `RUMOR{streamId, itemId, hopsRemaining, payload}` to `fanout` sampled members. Receipt deduplicates on `(streamId, sha-256(payload))` against a bounded seen-cache (4,096 entries, insertion-order eviction), so a pre-seeded item id cannot suppress an honest item; delivers the payload to the stream's registered handler; and forwards to `fanout` further members with `hopsRemaining - 1` while the budget lasts, excluding the peer it arrived from. The hop budget is the constant `GossipBus.DEFAULT_HOPS = 6`; a publisher may choose a smaller budget, and an inbound budget above the constant is clamped to it. `fanout` comes from the group advertisement's gossip parameters (default 3), and `period` (default 1 s) paces the anti-entropy channel (§5.1); v0.1.10 removed `maxViewSize`, because membership views are full and leased. Expected propagation is O(log N) rounds; the repository pins this with a seeded simulation suite.

*Lazy repair (SPEC v0.1.32 and v0.1.33).* Between members that advertise `wire.tree=1`, a member that hears a `HAVE` for an item it lacks keeps it in `Missing` and asks with a `GRAFT` when its wait ends. The wait reads the clock. Two rings of `GRAFT_RTT_SAMPLES` (64) samples, the graft round trips and the tree copies' delays after their first announcement, give the lateness, the longer of their two 90th percentiles; a member holds at most `SAMPLES_PER_MEMBER` (6) samples of a ring, and a new sample from a member at that cap replaces the same member's oldest. The base is the lateness, at most `GRAFT_BASE_MILLIS` (500 ms), and the spread window is twice the lateness, between `GRAFT_SPREAD_MIN_MILLIS` (250 ms) and `GRAFT_SPREAD_MAX_MILLIS` (4 s); before any sample the wait is 500 ms plus a spread over `GRAFT_SPREAD_COLD_MILLIS` (1 s). Later asks back off from `GRAFT_BACKOFF_MILLIS` (1 s) to `GRAFT_BACKOFF_MAX_MILLIS` (8 s), and an item stays wanted for `MISSING_HORIZON_MILLIS` (15 s) after its last announcement. `Missing.next` picks, at random, an announcer not yet asked this round, never the first heard while another is left, and one with fewer than `UNANSWERED_STRIKES` (3) unanswered asks in a row while another qualifies. The memory holds `MISSING_CAPACITY` (256) items in per-announcer shares (`Share`): when the memory is full, an announcer that would hold more than an even split gives up an item of its own share, any other announcer takes the room from the largest share, and a share gives up its oldest item that no other member named, the items another member also named last; `GRAFT_EVICTED`, `GRAFT_EVICTED_OWN`, and `GRAFT_EVICTED_OTHER` count the evictions. A tick sends at most `GRAFTS_PER_TICK` (16) asks. The member that answers a `GRAFT` sends the item with `hopsRemaining = 1`, and the asker forwards the item along its own eager edges with the same budget; such a copy prunes nothing, except an answer still due in `answersDue` after another copy came, which prunes the edge its `GRAFT` made. `repairCounters()` reports the asks by cause.

### 5.4 Gossip: the anti-entropy channel

Convergence is guaranteed by the pull channel. Any component may register a `ReconcilableState` under a stream id — registration returns a handle, one state per stream id per node, a duplicate is refused rather than substituted, and closing the handle deregisters (v0.1.11); rumor handlers under `onStream` follow the same rule — exposing three operations: `digest()` returns opaque bytes summarizing local state, `deltaFor(remoteDigest)` returns the delta the remote is missing (empty when nothing), and `applyDelta(bytes)` merges. Each anti-entropy round (once per gossip `period` per group, §5.1) sends `DIGEST{streamId -> digest}` for all registered streams to one random partner; the partner computes deltas and answers with a single `PULL_RESP`, which the asker applies only when it matches an outstanding digest exchange, and applies in the order it registered the streams, not the order the wire carries them (the canonical map order of wire v3 sorts shorter stream ids first, which would put `space:x` before `credential-revocations`; a node registers its revocation registries before any space attaches, so a late joiner judges a pull's records with the revocations the same pull brings). The ad-cache and every replicated space register themselves here, with the digest formats given in §6.2 and §7.5, and the revocation registry registers under `revocations` (§6.1). Rumors make dissemination fast; anti-entropy makes it certain.

### 5.5 Transports

The `Transport` SPI is `scheme()`, `dial(address)`, `listen(bindAddress, onAccept)`, and (v0.1.19) a defaulted `capabilities()`, yielding `TransportConnection`s that send and receive opaque frames and report an optional `attestedPeer()`. Peer advertisements carry endpoints as `(transport, address, priority)`; `PeerNode.listen(transport, bind, priority)` sets the priority a listener advertises. Dialers try a peer's endpoints in ascending priority, keeping the advertised order among equal priorities, and skip endpoints whose scheme no configured transport serves, so transports mix freely in one fleet and a peer that advertises `quic` and `tcp` side by side is dialed in the order it asked for.

| Binding | Scheme | Framing |
| --- | --- | --- |
| In-JVM loopback (`SimNetwork`, test-support) | `mem` | direct delivery; also drives the deterministic simulation tests |
| TCP | `tcp` | 4-byte big-endian length prefix per frame, maximum frame 8 MiB, one virtual thread reading per connection |
| TLS over TCP (`TlsTcpTransport`) | `tls` | the TCP framing inside TLS 1.3; presents the identity-endorsed channel certificate of SPEC §5.6 and attests the remote end, or validates to a CA trust store with CRLs in the enterprise mode |
| QUIC (RFC 9000, `agentspaces-transport-quic`) | `quic` | one bidirectional stream per peer connection carrying the same 4-byte length-prefixed frames; ALPN `aspace/1` |
| DTLS 1.2 (RFC 6347, `agentspaces-transport-dtls`) | `dtls` | one association per peer connection; frames fragmented into recovery-sublayer `DATA` PDUs, one per DTLS record, with selective-repeat acknowledgement, in-order delivery, and Connection ID (RFC 9146); no length prefix |
| WebSocket (RFC 6455, `agentspaces-transport-http`) | `ws` | one binary message per frame, subprotocol `aspace.1`, 8 MiB cap (1009 on an oversize message, 1003 on a text one); Netty HTTP codec; browsers admitted only from the listener's `allowed-origins` (`OriginPolicy`); unattested, so SESSION-mode peers run SPEC §5.6 session attestation in band |
| WebSocket over TLS (`agentspaces-transport-http`) | `wss` | the `ws` binding inside TLS 1.3 with the `tls` binding's identity modes; a dialer with no certificate (a browser) is accepted as unattested |
| HTTP exchange (`agentspaces-transport-http`) | `http` | `POST /open` (201, `Location: /s/<sid>`), `POST /s/<sid>/up` carrying a CBOR batch of frames under `Aspace-Seq`, `GET /s/<sid>/down` long-polled under `Aspace-Ack`, `DELETE /s/<sid>`; for intermediaries that break WebSocket; same port as `ws` (`HttpServerCore`) |
| HTTP exchange over TLS | `https` | the exchange inside TLS, paired with `wss` as `http` is with `ws` |
| WebRTC data channel (`agentspaces-transport-webrtc`) | `webrtc` | one ordered, reliable data channel `aspace/1` per peer connection, frames as one-byte-header chunks of at most `min(16 KiB, maxMessageSize) - 1` bytes, reassembled to 8 MiB; signalling over `aspace:cap/rtc-signal`, attestation by the signed DTLS fingerprint; libdatachannel behind the `DataChannelEngine` seam. The endpoint `(webrtc, "sig", p)` names no address, so the binding is *signalled* (`Transport.signalled()`, v0.1.21): a node never dials it from inside a send, which takes the relay, and dials it from its tick once more than `frames-per-minute` (30) frames crossed a relay to or from the member in a sliding minute, retrying a failed dial after `retry-after` (5 minutes) at the earliest (`PeerNode.Builder.relayOffload`, `agentspaces.transport.webrtc.offload.*`; settings, not caps) |

The QUIC binding runs on Netty's incubator QUIC codec over quiche, in the three identity modes of the TLS binding. Unattested (`new QuicTransport()`): the server handshakes with an ephemeral, per-process EC P-256 certificate assembled by a pure-JDK X.509 DER writer (`EphemeralCertificate`, used in this mode only) and dialers do not verify it, because peer authentication is the frame signature layer (§3). Identity-endorsed (`QuicTransport(PeerIdentity)`): both ends present the identity's `ChannelCertificate` and attest the leaf. Enterprise-CA (`QuicTransport(identity, ServingCredential, ChannelTrust)` and `QuicTransport.withRefreshableTrust(identity, serving, Supplier<ChannelTrust>)`, v0.1.13): the node presents the CA-issued chain and attests a remote end only when its full presented chain validates under the trust, consulted afresh per connection. Session posture (v0.1.13): both SSL contexts set `earlyData(false)`, `sessionCacheSize(1)`, and `sessionTimeout(1)`, and the client engine is host-less so its session cache has no key; quiche 0.0.75 exposes no switch to stop a server issuing tickets to third-party clients, which is harmless because no attestation rests on a resumed session. The dialer attests when its connect future completes; the accepting side attests lazily on the first `attestedPeer()` call, on the channel's event loop, by which time a frame has arrived and the handshake has completed, so a stream initialized mid-handshake cannot read an honest member as unattested. The server's per-connection handler is `@Sharable` (a non-sharable one made each listener accept a single connection until v0.1.13). Idle timeout is 60 s, dial timeout 10 s, flow-control windows sized to carry the 8 MiB maximum frame. OS-activated profiles select the quiche native classifier for macOS; tests skip where `Quic.isAvailable()` is false. The incubator codec has moved into Netty 4.2, so a migration is pending.

The DTLS binding (v0.1.19) runs on BouncyCastle's DTLS implementation (`bctls-jdk18on`, the low-level `DTLSClientProtocol` and `DTLSServerProtocol`; BouncyCastle's JSSE provider has no DTLS), in the three identity modes of the TLS binding plus `DtlsTransport.unattested()`, which encrypts with an ephemeral certificate and never reports `ATTESTING`. BouncyCastle carries the handshake, its flight retransmission, the stateless cookie check (`DTLSVerifier`, rotated every 60 s), the records, and Connection ID; the binding supplies policy (AEAD ECDHE suites, extended master secret required, no resumption, renegotiation, or Heartbeat) and the recovery sublayer of SPEC §5.5 (`Recovery`, a pure state machine on a clock: RFC 9000 ACK ranges, RFC 6298 timing, RFC 9002 loss thresholds, a 64-PDU window, a 64-frame and 16 MiB receive bound, 15 s keepalive, 60 s idle). One listener socket demultiplexes by Connection ID, then by source address, and admits a new source only through the cookie check, a per-source token bucket (8 ClientHellos per second), and a half-open bound (1,024); an association whose dialer's address changes follows it on an authenticated, newest, CID-bearing record, sending at most three times what it received until the new path acknowledges data. The Spring starter and the Micronaut factory wire the binding from `agentspaces.transport.dtls.*` (and QUIC from `agentspaces.transport.quic.*`), sharing the `agentspaces.transport.tls.*` credential and trust; the module is pure Java, so it runs wherever the JDK does.

## 6. Layer 2: Advertisements and Discovery

### 6.1 The advertisement family

Advertisements are typed records sharing the envelope fields `(id, issuer, group, issued, ttl)` plus type-specific bodies: `PeerAdvertisement` (endpoints, roles, resource hints), `GroupAdvertisement` (name, membership policy, default conflict strategy, gossip parameters `{fanout, period}`), `SpaceAdvertisement` (space name, schema hints, strategy, `admission: GROUP | ALLOWLIST`, `replication: FULL | TAG_SHARDED`; the last two appended in v0.1.10 with `GROUP` and `FULL` as the decoded defaults), `CapabilityAdvertisement` (type URI, version, endpoint binding, parameters), `AgentCard` (agent id, description, goals, consumed and produced schema names, cost hints, `spaceBindings: map<consumedSchema, spaceName>`, appended in v0.1.10 and empty when absent, `agentPublicKey: bytes?`, appended in v0.1.11 and omitted when absent — the peer-certified key of an attested agent, pinned by `agent_card_with_key_cbor`; `AgentCard.attested()` reads it; `actions: list<CardAction>?`, appended in v0.1.13 and omitted when absent, each `CardAction(name, description, consumes, produces, space?, kind)` declaring one bound method; and `agentCertificate: AgentCertificate?`, appended after `actions` in v0.1.13 and omitted when absent, the peer's certificate for `agentPublicKey`, which a cache verifies under the card issuer's key at the card's `issued`), and `AssetCard` (asset name, source URI, declared data shape, freshness, access binding). Recommended TTLs: peer ads 10 minutes, agent, space, and capability cards 15 minutes, group ads 24 hours.

`RevocationAdvertisement` (SPEC v0.1.9) is an advertisement type that never enters the ad-cache. `DiscoveryService.publish` of one routes it to the group's `RevocationRegistry`, which verifies the signature and the signer's authority; an accepted revocation is gossiped on the stream `revocations` (`DiscoveryService.REVOCATION_STREAM`) and reconciled by anti-entropy, and a refused one is never gossiped. Enforcement beyond dispatch (v0.1.13): `GroupMembership.refuse(Predicate)` is bound to the registry, so `onPeerAdvertisement` never admits a revoked peer, and `PeerNode.admitAdvertisement` and the `peers` forward filter refuse its ad; `RevocationRegistry.addListener` lets `DiscoveryService` purge the revoked issuer (`AdCache.purgeIssuer`) and `AdCache.refuseIssuers` keeps it out; `ReplicatedSpace` refuses a state whose actor is revoked (the claim holder for a completion, the record issuer otherwise) and a claim whose holder is revoked, records the refused digest line in a bounded `refusedAck` map, and appends each as `a:<line>` to its digest, which `deltaFor` treats as already held.

Registry order (v0.1.13): `RevocationRegistry` keeps one `Accepted(ad, signed, rank, hash)` per peer and replaces it only when the candidate outranks it — rank (`FOUNDER` 3, a record carrying evidence `TRUST_ROOT` 2, else `OTHER` 0), then later `issued`, then larger hex SHA-256 of `adBytes`; `verify` refuses a `successor` from anyone but the founder. `RevocationValidator.anyOf(...)` combines validators and `RevocationValidator.caRooted(Supplier<ChannelTrust>)` accepts a revocation whose appended `evidence` decodes as `RevocationEvidence{chain: List<DER>, crl?: DER}` (≤ 4 certificates, CRL ≤ 64 KiB, ≤ 96 KiB in all) and for which `ChannelTrust.status(chain, ad.issued(), [evidence CRL])` is `TrustStatus.Revoked` naming `ad.revoked()` with `authorizesPeerRevocation()`. `ChannelTrust.status(chain, at[, extraCrls])` returns `Good | Revoked(peer, CRLReason, revokedAt) | Undetermined | Untrusted | Expired | NotYetValid | Malformed`: PKIX at the given date without revocation, then with the trust's CRLs plus the extra ones (an unverifiable or stale CRL yields `Undetermined`); `attest` is `status(chain, now)` is `Good`, except under `strictOnline()`, whose online path now also adds the cached CRLs. `TransportConnection.remoteChain()` (default empty) returns the remote end's presented chain; TLS keeps it from the handshake and QUIC reads it where it attests. `PeerNode.Builder.channelTrust(Supplier<ChannelTrust>)` makes the node judge each chain on `attach` and every chained connection (a weak set) whenever the supplier yields a new instance, checked each tick; a `Revoked` with an authorizing reason closes the link and, once per peer (`caRevoked`), issues a `RevocationAdvertisement` with reason `ca:<crl reason>` and the evidence into every joined group, gossiped when the group's validator accepts it. `ReloadingChannelTrust(authorities, crlFiles, refresh, strictOnline, clock)` re-reads CRL files when their modification time or size changes, at most once per `refresh`, keeping the instance otherwise and the last good trust on a read failure. Under Spring Boot the trust is built before the node, the transport is `TlsTcpTransport.withRefreshableTrust`, `agentspaces.transport.tls.crl-refresh` (5m) paces it, and `agentspaces.transport.tls.revocation-validator: founder-or-ca` installs `anyOf(founderRooted(), caRooted(trust))`; it fails at startup without a trust store.

`CredentialRevocation` (SPEC §6.1, v0.1.13) is the advertisement type for everything else certified: `Target{kind, agent?, keyFingerprint?, x509Issuer?, x509Serial?, certificateFingerprint?, credentialHash?}` with kinds `AGENT`, `AGENT_KEY`, `X509_LEAF`, `JOIN_CREDENTIAL`, canonical id `aspace://<group>/revocation/<kind>/<canonical>`, `reason` from `REASONS`, `effectiveFrom?` (≤ `issued`), `evidence?`. `DiscoveryService.publish` routes one to `GroupRuntime.credentialRevocations()`, a `CredentialRevocationRegistry` (digest lines `c:<kind>:<canonical>=<hash>`, `MAX_RETAINED` 4096, the same total order with `OWN_PEER` 1 for an agent's own peer, ranked by a `CredentialRevocationRegistry.Validator`, `defaults()` founder-or-own-peer), gossiped on `credential-revocations`. `GroupRuntime.revocationView()` is the `api.security.RevocationView` over both registries: `revoked(PeerId)`, `refuses(AgentId, agentKey?, signingTime?)` (peer revoked, or an `AGENT`/`AGENT_KEY` record whose `refusesAt(signingTime)` holds: always under `key-compromise` or a null time, else at or after `effectiveSince()`), and `revoked(AgentId, key)` = refuses at any time. Enforcement points: `ReplicatedSpace.mergeClaim` and `applyAuthorizedClaim` (null time), `refusedForRevocation` (the record issuer at the state's `signedAt` else the record stamp, with the record's and the state's agent keys; the claim holder for a completion), `prepareWrite`, `tryTakeOnce`, and `Handle.renew` for local actors; `AdCache.refuseAgents(view)` and `purgeAgent`; `GroupKeyDistributor` via `CapabilityPipes.revocations()`; `VoteCapability` tally via `ReplicatedSpace.revocationViewOf(space)` (overridable with `revocations(view)`); `GroupScopedAuthorizer(inner, view, membership?, self)`, which the starter wraps around every group's authorizer (with membership required for the shared OIDC one); `PeerNode.admitsInvite` (refuses a revoked credential's hash and records which credential admitted each member, so `onCredentialRevoked` evicts it); and `PeerNode.attach` plus `onCredentialRevoked` for `X509_LEAF`, closing links whose leaf DER hashes to a revoked fingerprint. Issuance: `GroupRuntime.revokeAgent`, `revokeAgentKey`, `revokeJoinCredential`, `revoke(target, reason, effectiveFrom)`, and the facade's `GroupContext.revokeAgent|revokeAgentKey|revokeJoinCredential`; the facade unbinds a revoked local agent (`AgentBinder.unbind`).

### 6.2 The signed wrapper and the cache

An advertisement travels as `SignedAdvertisement{advertisement, publicKey, signature}`: the issuer's raw key and its Ed25519 signature over the advertisement's canonical CBOR. Receivers verify key-hash-equals-issuer and the signature before caching (`AdCache`); the cache stores at most one advertisement per id, replaces only when `issued` is newer, and evicts on TTL expiry at read time, so an expired advertisement is never returned and never forwarded.

The cache registers with anti-entropy (§5.4) under the stream `ads`. Its digest is 32 bytes of SHA-256 followed by the UTF-8 key list, one `<adId>=<issuedEpochMillis>` line per cached ad; `deltaFor` returns the stored signed ads whose key lines the remote digest lacks, so a newer reissue of the same id also transfers. The `ads` rumor stream carries a forward filter that re-verifies through `AdCache.accept`, so an expired, tampered, or mistyped advertisement is never re-forwarded, and `publish` gossips nothing its own cache rejected. The cache holds at most `AdCache.DEFAULT_MAX_ENTRIES` (8,192) advertisements; a node with the RENDEZVOUS role sizes it at `RENDEZVOUS_CACHE_MULTIPLIER` (4) times that, 32,768, through `DiscoveryService.create(runtime, codec, self, clock, roles)`. SPEC v0.1.32 adds a byte budget beside the entry count (SPEC §6.3), which §11 lists as not yet built.

### 6.3 Discovery queries

`find(type, predicate)` is a local cache scan. `remoteFind` validates the predicate against the advertisement type first, so a predicate naming an unknown field throws `IllegalArgumentException` before anything is published, then escalates in parallel: a direct `QUERY` frame to each known RENDEZVOUS-role member and a scoped gossip rumor on the stream `ad-query` under the normal hop budget, in the same pass. Any peer receiving the query answers with `QUERY_HIT` carrying its matching stored ads (signed wrappers, §6.2) directly to the asker, who verifies each before merging it into its own cache and re-running the local scan; a peer never answers its own query. Rendezvous peers differ from ordinary members only in cache size and in being asked directly; correctness never depends on them.

## 7. Layer 3: The Replicated Space

### 7.1 The entry record

```
EntryRecord {
  entryId    : EntryId (UUID)
  spaceId    : SpaceId
  type       : string            (schema name, §9.1)
  payload    : bytes | null      (canonical CBOR of the entry; <= 64 KiB inline)
  payloadRef : string | null     (CID, for payloads over the inline limit)
  issuer     : AgentId
  issued     : HlcTimestamp
  lease      : LeaseInfo { holder: AgentId, expiresAtMillis, kind: WRITE | TAKE }
  tags       : map<string,string>
  sig        : bytes             (§7.2)
  keyEpoch   : int64 | absent    (v0.1.13; the content-key epoch, omitted for epoch 0 and unencrypted spaces, §7.9)
}
```

Exactly one of `payload` and `payloadRef` is set; the inline limit is 65,536 bytes and the writer's space enforces it, storing larger payloads in the block store and writing the CID (§7.8).

### 7.2 The record signature

The writer signs `SignView = (entryId, spaceId, type, payload, payloadRef, issuer, issued, tags, keyEpoch?)` in canonical CBOR, `keyEpoch` appended in v0.1.13 and omitted when absent so epoch-0 and unencrypted records sign exactly the v0.1.12 bytes (golden `sign_view_cbor`): the record's immutable identity, excluding the lease (which changes across takes and renewals) and the signature field itself. Replicas verify the signature and that the issuer key hashes to the record's issuing peer before any merge.

**Subordinate identities (v0.1.11).** The record signer is the writer's `AgentIdentity` (`agentspaces-api` SPI: `id()`, `publicKey()`, `sign(bytes)`, `certificate()`), given to the space through `ReplicatedSpace.Builder.writer(AgentIdentity)`; the four-argument `builder(runtime, name, identity, agentName)` means `.writer(identity.agentIdentity(agentName))`, the peer-signed form with no certificate, so nothing that compiled before changes behaviour. `PeerIdentity.subordinate(name)` (and its `(name, issued, ttl)` and `(name, KeyPair, issued, ttl)` overloads) yields an identity with a fresh or supplied Ed25519 pair and an `AgentCertificate(agent, agentPublicKey, issued, ttl, peerSignature, encryptionPublicKey?)` the peer signs over the record minus its signature (`AgentCertificates.sign`). `EntryStateDto` gains one appended, nullable field, `agentCertificate`, beside `issuerPublicKey`; it is omitted from the wire when absent, so a fleet that never opts in is byte-identical to the pre-certificate DTO and the earlier golden vectors hold unchanged. `issuerPublicKey` is always the *peer* key. `verifyRecord(record, issuerKey, certificate)`: the peer key must hash to the record's issuing peer; with no certificate the record verifies under the peer key; with one, `AgentCertificates.verify` checks the peer signature over the certificate body, that the certificate names exactly the record's issuer, that the issuer's peer is the peer the key hashes to, and that the certificate covers the record's signing time (`AgentCertificates.verifyCovering(certificate, peerKey, expected, signingTime)`, v0.1.13 and SPEC v0.1.30, E4: `AgentCertificate.covers(t)` is `issued <= t < issued + ttl`; the signing time is `record.issued().physical()` for records, `claim.stamp().physical()` for claims, and `signedAt.physical()` for an agent-signed state (v0.1.31, rule F4 of SPEC §9.2), and the check sets no bound on how far it leads the receiver's clock, because the replica judges that lead afterwards by the far-future rule of §7.5 and §7.6). `AgentCertificates.verifyAt(certificate, peerKey, expected, signingTime, receiverNow)` adds the bound `signingTime <= receiverNow + HybridLogicalClock.MAX_DRIFT_MILLIS` and serves the checks that keep it: an agent card's attestation (`AdCache`) and a group key request (§8.7). The clients split the check the same way: Python `verify_agent_certificate_covering` and `verify_agent_certificate_at`, TypeScript `verifyAgentCertificateCovering` and `verifyAgentCertificateAt`, and Ruby `Certificates.verify_covering` and `Certificates.verify_at`. A record carrying a certificate but a peer-key signature is refused. The replica keeps the certificate per entry beside the issuer key and forwards it verbatim in anti-entropy, and `Space.Issued<T>` gains a third component, `attestation`, `PEER_ASSERTED` or `AGENT_ATTESTED`, whose two-argument constructor defaults to the former. A view's state transitions on an agent-attested entry are signed by the acting agent's key (v0.1.13, §7.4), and its take claims are signed by its agent (§7.6). **Views (v0.1.11).** `ReplicatedSpace.as(AgentIdentity)` returns a `Space` view, a small delegating class, over the same replica: `writeAs`, `takeAs`, `completeInternal`, and `adoptClaimAs` take the acting identity, so a view's records are issued and signed by its agent (attested when subordinate), its claims name its agent as holder (`TakeClaim.holder`, `LeaseInfo.holder`), `EntryHandle.renew` and `TakenEntry.renew` act as the identity that made them, and `requireAdmitted` judges the acting agent, so ALLOWLIST and CREDENTIAL apply per view. Reads, subscriptions, the HLC (one clock per node, seeded by the handle's own writer), the gossip registration, and the digest are the replica's. `as(...)` refuses another peer's agent and returns the handle itself for its own writer. `AgentBinder` takes an identity factory (`Function<String, AgentIdentity>`, default `identity::agentIdentity`; `identities(...)` to replace it) and, for a subordinate identity, hands `@SpaceRef` fields and the take/notify loops `space.as(identity)`; `AgentSpaces(identity, clock, identities)` threads it to every group's binder, and the starter builds it from `agentspaces.identity.agent-keys` (`peer` | `subordinate`). `VoteCapability`'s constructor check is satisfied by a view whose writer is the voter. Renewal (v0.1.13): the SPI gains `certificateCovering(Instant)` and `renewIfDue(Instant)`; `PeerIdentity.renewingSubordinate(name[, KeyPair], ttl, InstantSource)` returns a `RenewingAgentIdentity` with a fixed key that re-issues its certificate once half of `ttl` has passed, lazily on every `sign`, `certificate`, and `certificateCovering` call (the binder's `refreshCards` is an extra driver), keeping up to 256 issued certificates. `prepareWrite` and claim signing attach `certificateCovering(stamp)` and throw `IllegalStateException` when none covers the stamp. Under the starter, `agentspaces.identity.agent-keys=subordinate` builds renewing identities on the fabric clock with `agentspaces.identity.agent-certificate-ttl` (default 24h). Keystore and cards (v0.1.13): `AgentKeystore.at(dir).signingKeys(peer, name)` and `encryptionKeys(peer, name)` load or mint per-agent pairs through `KeyFiles` (names validated against `[A-Za-z0-9._-]{1,64}`, temp-file-and-rename writes with fsync, 0600 private files, a sign/verify or agreement probe on load, a half-written pair refused naming both files); `FileKeystore` loads through the same helper. Under the starter, `agentspaces.identity.agent-keystore` persists subordinate keys and is refused under `agent-keys: peer`; the `AgentIdentityFactory` bean (`agentspaces-agent`) is the replaceable seam. `AgentCard.agentCertificate` is filled by the binder with the certificate covering the card's `issued` (on build and every refresh), the card constructor refuses a certificate for another agent or key, and `AdCache.accept` verifies it with `AgentCertificates.verifyAt(certificate, issuerKey, agent, card.issued(), now)`. `LocalSpace.as(AgentIdentity)` returns a view whose writes and results are attributed to the agent, reported `AGENT_ATTESTED` for a subordinate one.

### 7.3 The replica state

Per entry, the replica holds `EntryState`:

```
EntryState {
  record    : EntryRecord
  adds      : set<Dot>                      Dot = (replicaId, counter>0)
  removes   : set<Dot>
  lease     : LwwRegister<LeaseInfo>        (HLC-stamped, last writer wins)
  completed : bool                          (monotone)
}
```

An entry is present when it is not completed and at least one add dot is unremoved (observed-remove set semantics: a withdrawal removes exactly the dots it has observed, so a concurrent re-add with a fresh dot survives). Merge is field-wise: union the dot sets, LWW the lease by HLC stamp, OR the completed flag. Merge is commutative, associative, and idempotent by construction, and the repository pins the CRDT laws with randomized convergence tests. The monotone completed flag is what makes a second `complete` unmergeable: once any replica records completion, every merge preserves it.

Tombstones are garbage-collected (`SpaceStateCrdt.gc`, SPEC §7.3). An entry is collectable when it is no longer live (completed, withdrawn, or past its write lease) and `leaseExpiry + 2 × maxLease <= now`, where `maxLease` is the largest lease the replica has observed, capped at 24 hours (`ReplicatedSpace.maxLeaseMillis`), or the `Builder.maxLease` override. Collection drops the entry state and prunes the issuer-key, claim, and signed-state maps in step; merge semantics are unchanged. A state re-offered by a lagging partner through anti-entropy is refused when `SpaceStateCrdt.collectable` already holds for it, so a collected tombstone never returns and a late joiner never receives one.

### 7.4 The state signature (authenticated transitions)

The record signature covers identity, so the mutable fields need their own authentication (SPEC §11a.4). Every state delta carries `stateSig`, an Ed25519 signature over `StateSignView = (spaceId, entryId, adds sorted by (replica, counter), removes sorted likewise, leaseStamp, leaseValue, completed)` in canonical CBOR. The authorized signer is implied by the transition: a state with `completed = true` must verify against the holder key of a valid signed take claim on that entry (carried in or already merged from the same exchange); every other state must verify against the record's issuer key. A delta whose state signature is missing, wrong, or signed by an unauthorized party is dropped before merging. For the completion branch the key comes from the receiver's own stored `SignedClaim` for the entry, so that claim must be holder-attested (`holderKey` hashes to the claim's holder) or no completion can ever verify there; a claim the ordered log committed is therefore stored with the submitter's key and signature exactly as they travelled in the log command (§7.6, §8.3). Anti-entropy forwards the most advanced stored actor-signed state verbatim rather than re-signing, because a relay is not the author; "most advanced" prefers completion, then more removes, then the newer lease stamp, then more adds. Agent-signed transitions (v0.1.13): `EntryStateDto` appends `stateCertificate`, `signer` (the AgentId encoded), and `signedAt`, and `StateSignView` appends `signer` and `signedAt`, all `@JsonInclude(NON_NULL)`. `signedDto(entryId, issuerKey, actor)` signs with `actor.sign` and attaches `certificateCovering(signedAt)` when the actor is subordinate, and signs with the peer key otherwise (byte-identical to v0.1.12). `verifyState` takes the authorized party (the claim holder for a completion, the record issuer otherwise) with its peer key; an agent-signed state must name that party as `signer` and pass `AgentCertificates.verifyCovering` at `signedAt` (v0.1.31, rule F4 of SPEC §9.2; the far-future rule of §7.5 then judges `signedAt`) before `stateSig` is checked under the certificate's agent key; a peer-signed state is refused when the party is agent-attested (the record has an `agentCertificate`, or the claim a `holderCertificate`). `Handle.renew` and `cancel` throw when the acting identity is not the issuer of an agent-attested entry. `OrderedTakes` accepts a holder `AgentIdentity` (constructor and `over(...)` overload); its `ClaimCommand` appends `holderCertificate`; `onCommand` installs through `applyAuthorizedClaim(..., certificate)`, whose `verifyClaim` is the same check gossip uses; the coordinator adopts as the holder (`adoptClaim(template, entryId, holder)`). `SpaceEvent` appends `actor`: the claim holder for `COMPLETED`, the issuer otherwise. `sweep` also drops `issuerCertificates` and `logDecidedEpochs` for collected entries.

*Verified signatures (SPEC v0.1.33 §11a.4).* `ReplicatedSpace` verifies records, states, and claims through `VerifiedSignatures` (`agentspaces-common`), which remembers up to `DEFAULT_CAPACITY` (4,096) signatures that verified, keyed by the raw key, the signature, and the SHA-256 of the signed bytes, the least recently used leaving first. A failed signature is never remembered. `mergeState` judges revocation, admission, certificate windows, and stamps on every copy after the signature check. `SpaceStateCrdt.liveRecords` builds an immutable state's live records once.

### 7.5 Replication channels

Each space registers a rumor stream `space:<name>` and an anti-entropy state under the same id, so there is one replica per space name per node: a second `ReplicatedSpace` for an open name fails in its constructor naming the stream, and `close()` deregisters both so the name can be opened again (v0.1.11). A rumor delta is `Delta{state?, claimEntry?, claim?}`: an entry state, a signed claim, or both, published with item ids `d:<entryId>` for state deltas and `c:<entryId>:<hlcStamp>` for claim deltas. The anti-entropy digest is UTF-8 lines `e:<entryId>=<stateHash>` and `c:<entryId>=<claimHash>`, sorted, followed by an `a:<line>` acknowledgement for each state or claim the replica authenticated and refused (a revoked actor), so partners stop re-offering it; `deltaFor` answers with `SyncDelta{states: [EntryStateDto], claims: map<entryId, SignedClaim>}` containing the stored signed states and claims whose lines the remote lacks. On receipt of any delta, claims merge first (a completion authenticates against the claim that must accompany or precede it), then states verify (§7.2, §7.4) and merge. `mergeState` refuses a state whose record `issued` stamp, `leaseStamp`, or `signedAt` is not acceptable (§1.4, SPEC §7.3; v0.1.30; `signedAt` judged alike in every implementation since SPEC v0.1.30, D1). It judges the stamps after `verifyRecord`, `verifyState`, and the revocation check `refusedForRevocation` pass, so the refusal names a signer and a revoked actor's state counts in no stamp counter (SPEC v0.1.30, E6), and before the far-future check, the admission check, the merge, and the clock. A state whose `leaseStamp` or `leaseValue` is null decodes and drops before all of these checks, counting nothing (E7); a state that omits either field breaks the record rule P1 of SPEC §9.1, so its delta does not decode and counts in `deltasUndecodable()` (v0.1.31). It drops the whole state and, once per distinct state, after verification, counts the refusal in `ReplicatedSpace.stampsLogicalRefused()` and reports the signer of the refused stamp through `runtime.reportMisbehavior`, the path its admission check uses, with the reason `logical counter above 65536`: the record's issuer when `issued` fails, and otherwise the party that signed the lease stamp and `signedAt`, the claim holder for a completion and the issuer for every other transition. It acknowledges the refused line in its digest as `a:<line>`, as it does for a revoked actor, so a partner stops re-offering the state (v0.1.30). Next it measures `issued`, `leaseStamp`, and the `signedAt` of an agent-signed state against `nowMillis() + MAX_DRIFT_MILLIS + PeerNode.FAR_FUTURE_SKEW_MARGIN_MILLIS` (SPEC v0.1.30, D4; `signedAt` since v0.1.31, rule F4 of SPEC §9.2, which `verifyState` reaches through `AgentCertificates.verifyCovering`, the certificate's validity window alone). A stamp at or inside that bound passes. A stamp past it by at most `ReplicatedSpace.FAR_FUTURE_HOSTILE_MILLIS` (one hour) defers the state: nothing merges, nothing reaches the clock, the digest acknowledges nothing, the replica strikes nobody, and `stampsFarFutureDeferred()` counts the first deferral of each distinct state in a second bounded set, `deferredOffers`; anti-entropy offers the state again and it merges once the wall catches up. A stamp further out is hostile: the replica refuses the state, acknowledges it, counts it in `stampsFarFutureRefused()` once per distinct state, and reports its signer, chosen as for a logical refusal, with `far-future stamp`. Each offer meets these checks afresh against `nowMillis()`, so a state refused as hostile merges when a partner offers it again after the wall has caught up, and the sets below only stop a second count (E5). Every refusal and deferral is keyed on signed content alone (D5): `stateOfferKey` is the entry id, the `issued` stamp, and the SHA-256 of the state's signed view, which sorts its dots and holds `signedAt`, so neither a re-offer by another path nor a re-ordering of dots counts twice. The once-per-state promise rests on `rejectedOffers` and `deferredOffers`, least-recently-used sets of `REJECTED_OFFERS_CAP` (4096) keys each, which refused and deferred claims share: a state evicted from one and offered again counts, and for a refusal strikes, again. A state within both bounds feeds `issued` and `leaseStamp` to the clock with `hlc.update`.

### 7.6 The take claim lattice

A take claim is `TakeClaim{epoch, stamp, holder, bid, expiresAtMillis}`, and claims for one entry form a join-semilattice under a total preference order: higher epoch wins (the epoch increments each time a lapsed entry is re-claimed); within an epoch the lower bid wins; among equal bids the lower `(stamp, holder)` wins, which is the deterministic arbitration; and among claims by the same holder, the later expiry wins, which is how renewal works. The merge always returns one of its two inputs, which is the property that lets a claim's holder signature (`SignedClaim{claim, holderKey, signature}` over the claim's canonical CBOR) survive any number of merges and forwarding hops intact; between two proofs of the same claim it keeps the holder-attested one. A `SignedClaim` is `{claim, holderKey, signature, holderCertificate?}` (v0.1.11): `holderKey` is always the holder's *peer* key and must hash to the claim's holder peer (`holderAttested()`), which is also what the completion branch of §7.4 authenticates against; without a certificate the signature verifies under that key, and with one (appended, omitted when absent, so a peer-signed proof is byte-identical to before) `verifyClaim` checks the certificate under the peer key for exactly the claim's holder, covering the claim's stamp by the certificate's validity window alone (`AgentCertificates.verifyCovering`, SPEC v0.1.30, E4), and the signature under the certificate's agent key, refusing a proof that carries a certificate but a peer-key signature. `ReplicatedSpace.claimProof(entryId)` exposes the stored proof; `applyAuthorizedClaim` has a certificate-carrying overload; `OrderedTakes` submits peer-signed proofs. Golden: `claim_delta_with_certificate_cbor`, `take_claim_agent_signature`, and the three `adv_claim_cert_*_delta` refusals.

A claim decided by the ordered log enters through `ReplicatedSpace.applyAuthorizedClaim` in one of two forms. `applyAuthorizedClaim(entryId, claim, holderKey, signature)` verifies the proof under the claim's holder and stores it verbatim, so the claim is holder-attested at that replica and can authenticate the holder's completion; it throws when the key is not the holder's or the signature does not verify. `applyAuthorizedClaim(entryId, claim)` stores a proof signed by the installing replica, which decides local arbitration but is never holder-attested and cannot authenticate a completion anywhere else. Either form applies the stamp rule of SPEC §7.4 before the claim reaches the lattice (v0.1.30), the attested form after its proof and revocation checks pass. A committed claim whose stamp is not acceptable never reaches the lattice or the clock: the replica counts the refusal in `stampsLogicalRefused()` once per distinct claim, reports the holder through `runtime.reportMisbehavior` in the attested form alone, since the other form carries no holder signature, and throws `IllegalArgumentException`, as it does for every other refusal of a committed claim. Either form records the claim's epoch as log-decided for its entry, and `mergeClaim` then refuses a different gossip-borne claim at the same or a lower epoch while still merging an identical one (the attestation upgrade a completion delta carries). The anti-entropy digest keys claims by content (`c:<entryId>=<claimHash>`), so a replica holding an unattested copy of a claim advertises it as present and is never sent the attested proof by sync; this is why the attested form is the one the coordinator must use (v0.1.11).

Because the lattice prefers the lower stamp, `mergeClaim` bounds the stamps it accepts (SPEC §7.4, v0.1.10). A claim whose stamp precedes the entry's `issued` stamp by more than `MAX_CLAIM_PREDATES_ISSUE_MILLIS` (= `HybridLogicalClock.MAX_DRIFT_MILLIS`, 600,000 ms) is refused; this compares two stamps and so decides identically on every replica. A claim that contests another holder's current claim is refused when its stamp is older than `now - MAX_DRIFT_MILLIS - settleWindow`. `mergeClaim` also refuses a claim whose stamp is not acceptable (§1.4), with the reason `logical counter above 65536` (SPEC §7.4; v0.1.30); like the first check, this one reads the claim alone and decides identically on every replica. Right after it, `mergeClaim` refuses a claim whose stamp lies more than `FAR_FUTURE_HOSTILE_MILLIS` past `now + MAX_DRIFT_MILLIS + FAR_FUTURE_SKEW_MARGIN_MILLIS`, with the reason `far-future stamp`, and it defers a claim stamped past that bound by at most the hour when the claim passes every other check, counting the deferral in `stampsFarFutureDeferred()` and striking nobody (SPEC v0.1.30, D4). `mergeClaim` reaches these stamp checks only after `verifyClaim` accepts the proof and the certificate and the holder passes the revocation check, so a revoked holder's claim counts in no stamp counter (SPEC v0.1.30, E6). `verifyClaim` verifies the holder's signature over `codec.toBytes(claim)`, the `TakeClaim` record in its declared component order, which equals the bytes received, since a claim map that arrived in another order never decodes (SPEC §9.1, P1; v0.1.31, rule F3 of SPEC §9.2, which replaces E13's re-encoding); the Python (`wire.canonical_claim`), TypeScript (`wire.canonicalClaim`), and Ruby (`Wire.canonical_claim`) clients sign that order. A bid is a finite double: `TakeClaim` refuses NaN and the infinities, and every implementation orders bids by `Double.compare`, so -0.0 ranks ahead of 0.0. Each refusal counts and strikes the signer once per distinct claim under the per-issuer quarantine rules, keyed by `claimOfferKey`, the SHA-256 of the claim's canonical CBOR with its entry id (D5): `stampsLogicalRefused()` for the limit, `stampsFarFutureRefused()` for a hostile stamp. A refused or deferred claim never enters the lattice, and the digest acknowledges no refused claim except under the revocation refusal (SPEC §6.1), as an `a:c:<entryId>=<claimHash>` line in a map of at most `REFUSED_ACK_CAP` (8192) lines that forgets the least recently refused first; TypeScript keeps the same lines under `MAX_REFUSED_ACK` (v0.1.31, R7). The sweep drops a lapsed claim on an entry the replica collected or never held (`dropOrphanedClaims`), so the claim map stays bounded under churn (R10); TypeScript drops such claims in `collectTombstones`, and Python and Ruby, which run no timer, prune them as a space delta arrives once the map holds at least 1024 claims and twice as many as the last scan left. `applyAuthorizedClaim` applies the limit alone, since a committed claim's arbitration must not depend on a member's wall time. The replica feeds the stamps of the claims, records, and leases it accepts to its clock with `hlc.update`, so remote stamps enter the bounded regime of §1.4, and a refused stamp never reaches the clock.

### 7.7 The take algorithms

`LEASE_RACE` (default): collect present entries matching the template; claim the first with `epoch = current + 1` (or 1) and `bid = 0`, stamped by the local clock; merge the signed claim locally; publish it; sleep one settle window (builder default 200 ms; deployments set it to about twice the gossip period); then check the merged winner. Winning means the local claim survived the lattice; losing returns empty and the caller retries elsewhere. At most one `complete` per entry can ever merge (§7.3); transient duplicate work remains possible across partitions, which is why the idiom prefers idempotent tasks.

`AUCTION`: the same lattice with real bids. Candidates are sorted by this agent's bid ascending and claimed cheapest-first (the CBAA task-selection rule); an unexpired incumbent claim may still be counter-claimed at the same epoch while the incumbent's settle window is open and the challenger's bid is strictly lower. The lattice then makes every replica agree on the lowest-bid claimant with deterministic tie-breaks, converging like CBAA/CBBA consensus over gossip rounds. Bid functions are application code; nothing cryptographic constrains them (SPEC §11 names lying bidders as an accepted, operationally mitigated threat). A space holds exactly one: `ReplicatedSpace.bidFunction` is single-assignment, the builder's value counting as the first, and a second assignment throws (v0.1.11); an AUCTION take on a space with none fails fast rather than bidding a default.

`ORDERED`: takes serialize through the Raft-backed ordered log (§8.3). The claimant submits `ClaimCommand{entryId, claim, holderKey, signature}` to the log; every member applies committed commands in log order through `OrderedTakes.onCommand`, which verifies the claim signature and accepts exactly when `claim.epoch == committedEpoch + 1` for that entry, a pure function of committed state, so every replica arbitrates identically no matter when it applies. The accepted claim enters the space via `applyAuthorizedClaim` without re-publication; the log itself is its replication channel. Once `OrderedTakes.take` has submitted a claim, it waits for the log's decision for a 3 s attempt window, even past the caller's timeout, so a claim the log commits late still hands the entry to its taker (SPEC v0.1.33 §9.4; `OrderedTakesClusterTest.aClaimTheLogCommitsAfterTheTakersTimeoutStillHandsTheEntryToTheTaker`).

`complete(taken, result?)` validates and prepares the result record fully before committing the completion, so a result that cannot be written (oversize without a block store, unserializable) never leaves an entry completed but resultless. The completion sets the monotone flag, publishes the actor-signed state (§7.4), and only then commits the prepared result write.

Reads take a `ConsistencyHint` (`agentspaces-space`): `read(template, hint, timeout)` and `readAll(template, hint, limit)`. `LOCAL`, the default, matches the replica as it stands; `FRESH` runs one anti-entropy pull (`GossipBus.antiEntropyTick` toward one random member) and then matches locally. The lease sweep of a `ReplicatedSpace` emits `EXPIRED` when a present entry's write lease lapses and `REAPPEARED` when a taken entry's take lease lapses, once per transition, so replicated spaces fire the same five `SpaceEvent.Kind`s (`WRITTEN`, `TAKEN`, `COMPLETED`, `EXPIRED`, `REAPPEARED`) as `LocalSpace`.

### 7.8 Content addressing

`CID = multibase-base58btc(sha-256(bytes))`. The block exchange stores blocks by CID; a replica missing a referenced block sends `BLOCK_WANT{cid}` to candidate holders (the record's writer first) and accepts a `BLOCK{cid, bytes}` only when the bytes re-hash to the CID, which makes integrity checking and deduplication the same mechanism. Reads never wait on a block (SPEC P7): a match that meets a record whose block is absent starts exactly one background fetch, a blocking `read` awaits that fetch within its own timeout, and `readAll` skips entries whose block has not arrived. A subscription event for such an entry fires when the block arrives rather than when the record merges. A state that merges before its block is local cannot decode the entry for its `WRITTEN` event; the replica starts the background fetch at that moment (as a read that misses the block also does) and fires the deferred event once the block is stored, so a `notify` subscriber learns of a large entry without anyone reading it (`LargePayloadTest.notifySubscribersSeeLargeEntriesWithoutAnyRead`).

*Roots and trees (SPEC v0.1.23 and v0.1.29).* A `payloadRef` beginning with `b` is a CIDv1 string, multibase base32 lower over `0x01`, the codec, `0x12 0x20`, and a sha2-256 digest. Codec `0x55` (raw) names a piece artifact: the digest of the concatenated piece hashes, moved by `aspace:cap/content-swarm` tags 1 to 7 against its manifest. Codec `0x71` (dag-cbor) names the root node of a persistent tree (SPEC annex H), moved by tags 8 to 11 with no manifest; a tree root's holding has `have` null and `count` the nodes held. The two are told apart by the codec alone: the tree payload implementation (`PdtPayloads`) refuses a raw-codec reference and the artifact one (`SpacePayloads`) refuses a dag-cbor one, and both answer `isBulk` for the `b` prefix. A node is a canonical DAG-CBOR map (RFC 8949 deterministic encoding, definite lengths, shortest integer forms, keys ordered by length then bytes, no floats or indefinite forms in the node's own layer, a link as tag 42 over `0x00` plus the binary CID, application items embedded as raw CBOR items spliced in and skipped over), at most 1 MiB, with at most 1,024 links, in a tree at most 64 levels deep; a blob chunk is raw bytes with no map. A decoder refuses a node over any bound, an unknown kind, codec, or multihash, a key outside the kind's schema, or a link item in a key position, by name. Every node is verified against its CID before use on every path: inline delta on a `PRef` head, `NODES` answer, store read after a restart, escalation read. A space that escalates a payload to a tree pins the root for the entry's life through the `ensure` and `release` calls of its bulk seam, does not seal the payload before escalation, and records the key ring's write epoch in `keyEpoch` (SPEC §7.1); the nodes travel sealed per `NODES` message under that epoch or, in `sealed-nodes` mode, are sealed deterministically per node into an `sn` envelope (`{k, ct, ep, ln, nc}`: the ciphertext, the epoch, the plaintext's links in the clear, and a nonce keyed under the per-epoch node key, HMAC-SHA256 of the plaintext) whose CID keeps the plaintext's codec; a keyless holder walks the links and serves the envelope and learns the tree's shape and the equality of sealed nodes, never a content (SPEC annex H).

*PDT 2 (SPEC v0.1.32).* The reference implementation builds PDT 2 in `agentspaces-content`, `agentspaces-pdt`, the new `agentspaces-store`, `agentspaces-agent` (the records), `agentspaces-planner` (`StoreChooser`), and the Clojure library `agentspaces-datascript`, with no change to `CborCodec`, `WellFormedCbor`, or the `WireEncoding` classes.

- *The level.* `Content.Builder.pdtLevel(2)` advertises `pdt` = `"2"` beside `trees` = `"1"`; `Content.pdtLevel(peer)` reads a member's newest unexpired advertisement, and every level-2 send checks it. `Messages.decode` reads tags 1 to 12 through `CborCodec.fromWire`, `peekTag` routes a frame by its first bytes before the strict read, and `Content.onFrame` counts a broken piece message or manifest record in `Stats.pieceMessagesDropped` and a broken tree message, an unknown tag, or an undecodable payload in `treeMessagesDropped`. `Messages.Nodes.violation` refuses a sealed answer with deltas, and `Messages.TreeEnd.violation` a sketch beside any reason but 5.
- *Pieces by hash.* `HashPieceStore` names each piece by its sha2-256 under a two-character prefix (`pieces/ab/<64 hex>`), keeps a per-root `index.cbor` from `(root, index)` to hash, and counts references per hash, so a second artifact that shares pieces with a held one fetches only the rest; `PieceStore.open(Manifest, table)` seeds the root's `have` bitfield from the hashes it holds, and the starter selects it as `agentspaces.content.store.backends: hash`. `Content.shareTree` and `Pdt.share` write a holding or a head of the same root into a second group.
- *The tree server.* `TreeServer` answers `CHALLENGE` pick by pick under the `CONTENT_FETCH` grant of each pick, answers a sketch `TREE_WANT` through `SketchServer` (negentropy in `tree/sync/Negentropy`, RIBLT in `tree/sync/Riblt`, the set in `SketchSet`), and attaches frames from `ChunkDeltas` only to plaintext answers of a `TREE_WANT` whose haves show the base. `TreeFetchSession` rebuilds each frame through `Dcz.decode` (on `zstd-jni` 1.5.7-16) and verifies the chunk against its CID, and after one frame from a source that does not open it opens no later frame from that source. `SketchSession` drives the asker's rounds under one request id.
- *Blobs.* `BaoOutboard.of` hashes a blob's identity and outboard in one pass over the 16 KiB chunk groups on a shared pool of daemon threads in pure Java (`GroupHasher`), and its result does not depend on the thread count. `PBlob.openVerified(offset, length)` reads a window through `VerifiedWindow`, which walks the `bo` nodes of the window's groups to the identity and delivers each group only when its chaining value verifies. `ChunkDeltas` keeps a frame for the first 16 chunks of an edit, only when the frame is under half its chunk, for one hour, in a table of at most 16 MiB, and only while `Content.framesReachAMember()` says another member advertises level 2.
- *Refs.* `Refs.writeAncestry` stores the `vg` node beside the delta and names it in `pdt.ancestry`; `MetaStore` keeps pins and retention as `meta:<name>` records in the pack, so a restart keeps them. `RefKind.version` writes `PRef.v` 2 for a `db` ref, a relaxed vector (`values/Rrb`), and a ref whose values pass through `PText.codec`. `PushPublisher` and `PushReceiver` carry eager push, `Refs.headsLate()` counts heads whose root still loads, and the tick retries a failed head fetch with backoff (SPEC §9.4). A read waits only for the live heads that no head it can load supersedes, and skips a superseded head that has not loaded without counting it. A merge's walk and `Ref.history` ask the heads' issuers and the writer of every version the engine knows, as preferred sources (`Refs.chainSources`), for the chain nodes the store lacks, and `Refs.chainNode` keeps a chain node that has not arrived, forgetting one only when its bytes are held and unusable (SPEC v0.1.33, annex H). `Refs.share` into a second group with its own store fetches the rest of a partly held tree before it copies it, and throws `NodeUnavailableException` naming the root when the rest does not arrive within the load timeout.
- *The store.* `ContentStore` publishes the `content-store` card through a `ConnectorRuntime`, takes `SignedPin` entries under `LEASE_RACE` after `judge` checks the consent, the deadline (`Stores.PIN_ENTRY_LEASE` plus `ContentStore.DEADLINE_SKEW`), the policy (`StorePolicy`), and the take-once rule, holds the root, writes the `StoreReceipt`, charges `StoreLedger` per requester, and reconciles held roots with the next other store every `reconcileEvery` (10 minutes). On the requester's side `Stores` signs every pin it writes (`Pdt.Builder.identity`), chooses stores through `StoreChooser`, challenges with `SecureRandom` picks, and replaces a struck store's roots. Spring binds `agentspaces.store.*` and Micronaut `micronaut/store/`.
- *DataScript.* `agentspaces-datascript` implements `persistent-sorted-set`'s `IStorage` over CIDs (`CidAdapter`), so a fold writes its dirty path through one `PDb.Writer` batch, and `datascript-conn` transacts through a `db` ref (`Refs.dbRef`), linear by default; `values/PSortedMap` and `values/DatomOrder` give Java the `dn` layout and DataScript's three orders, and `refs/DbMerge` merges two heads by datoms.

### 7.9 Confidentiality and shards

With a group content key configured, payloads are sealed AES-256-GCM as `nonce || ciphertext || tag` with associated data `spaceId + "|" + entryId` binding the ciphertext to its entry, and encryption happens before signing so the record signature covers the ciphertext. The key is a `GroupKeyRing` (`agentspaces-common`, v0.1.13): `Builder.groupKey(key)` is a ring holding the key as epoch 0, and `Builder.keyRing(ring)` shares one ring across a group's spaces. A record sealed under epoch n ≥ 1 sets the appended `EntryRecord.keyEpoch` and uses associated data `spaceId|entryId|n`; `writeEpoch(now)` picks the newest held epoch whose cutover has passed, refusing once an announced newer epoch has been missing for `writerGrace` (1h) past its cutover; `sealingKey` breaks a same-epoch race by the lowest hex `sha256(epoch|rotator)`; `openingKeys` tries every key held for the named epoch and reports a missing epoch (throttled to once a second) to `onMissingEpoch` listeners; `withLease` keeps the record's epoch. Keyless members verify, store, and forward everything and decode nothing. A tag-sharded replica stores only entries whose tags satisfy its predicate; for entries it drops, it remembers `(entryId, stateHash)` so its anti-entropy digest still acknowledges them and partners do not endlessly re-offer.

### 7.10 Advertisement, admission, and read-only

A `ReplicatedSpace` built with `Builder.advertise(DiscoveryPublisher)` (a `DiscoveryService::publish` fits) publishes a signed `SpaceAdvertisement` on construction with id `aspace://<groupId>/<name>`, the strategy, the `Builder.schemaHints` types, the admission rule, and the replication mode, under `Builder.advertisementTtl` (default 15 minutes). `refreshAdvertisement()` reissues it and returns nothing once the space is read-only, so the advertisement's lapse is the release signal; any member finds the space with `find(SpaceAdvertisement.class, …)` by name.

`Builder.admission(SpaceAdmission)` sets the admission rule, and the older `admission(Admission, Set<AgentId>)` delegates to it. `SpaceAdmission` is `boolean admits(AgentId agent, Scope scope, long nowMillis)` with `Scope { WRITE, TAKE }`, plus `rule()`, the `SpaceAdvertisement.Admission` the advertisement carries (a predicate cannot be inferred from bytes), and `strikesOnRefusal()`, default false. Four rules ship. `group()`, the default, admits every member. `allowlist(Set<AgentId>)` restricts writers and strikes on refusal: a local `write`, `take`, or `complete` by an unlisted agent throws `SpaceAdmissionException`; an inbound record or claim from an unlisted agent is dropped and reported; reads and subscriptions stay open to the group. `credentials(PeerId issuer, CredentialIndex index)` admits the issuer always and any other agent for a scope when the index holds a live credential for that agent and scope. A credential is a `SpaceCredential(AgentId agent, Set<Scope> scopes)` entry of the reserved type `ai.badmonkey.agentspaces.space.replicated.SpaceCredential#v1`, its scopes normalised to an `EnumSet` and never empty so the record encodes deterministically (golden vector `space_credential_record_cbor`); the issuer writes it with `ReplicatedSpace.grant(agent, scopes, validity)` under a lease equal to `validity` and cancels it with `revoke(agent)`, and `grant` on any node other than the issuer throws `SpaceAdmissionException`. The `CredentialIndex` is maintained from the replica's own CRDT state as credential records merge, expire, or are cancelled; a `SpaceCredential` record whose issuer is not the configured issuer is dropped and struck. Credential records replicate to every tag-sharded replica regardless of the shard predicate, and the type is registered on every replica but excluded from the advertisement's schema hints. Tag conditions (v0.1.14): both implementations judge `Template.tagConditions()` against `EntryRecord.tags` after the schema-name comparison and before decode (`ReplicatedSpace.decodeIfMatches`, `LocalSpace.matchesLocked`) on every verb and on subscription delivery; `readAllEntries` returns `Space.Entry<T>` views (`EntryView`) built from the record; `complete(taken, result, lease, tags)` threads the tags into the prepared result write; `SpaceEvent.details` carries the same view for every delivered kind; `ReplicatedSpace.recordOf(entryId)` returns the record while the entry is present (available or claimed) and empty once completed; `recordOf(entryId, true)` answers from the tombstone for a completed entry too, which the ordered join needs to learn the key of a ticket whose taker finished before this member saw its claim commit. `authorizer(Authorizer, spaceName)` asks `permits(agent.peer(), SPACE_WRITE or SPACE_TAKE, spaceName)` (§4). `Builder.admission(CREDENTIAL, set)` makes this node the issuer, the founder default; `Builder.admission(AUTHORIZER, set)` throws, since an `Authorizer` instance is required.

Remote admission is judged per transition in `mergeState` and `mergeClaim`, after signature verification so a refusal is attributable: a new entry needs its issuer's `WRITE`, a completion of a known entry needs the claim holder's `TAKE`, a lease renewal needs the issuer's `WRITE`, and a withdrawal needs nothing. A known entry's other states are not re-judged, so a lapsed or revoked credential cannot retroactively drop work it admitted. A refusal strikes only when the rule's `strikesOnRefusal()` is true, which holds for `ALLOWLIST` alone; under `CREDENTIAL` and `AUTHORIZER` the credential or token may simply not have arrived yet, so the delta is dropped without a strike and anti-entropy re-offers it on the next round. A local `write`, `take`, or `complete` that any rule refuses throws `SpaceAdmissionException`.

`Builder.founderLease(duration)` starts a founder deadline on the space's clock, and `markReadOnly()` sets the flag directly; `renewFounderLease(extension)` extends a running lease and throws `SpaceReadOnlyException` once the space is read-only. A read-only space throws `SpaceReadOnlyException` from `write` and `take`, serves reads and subscriptions, and still accepts a bare `complete` so an in-flight take can finish. Collection of a read-only space after its longest entry lease is not implemented; the space object stays attached until its host closes it.

## 8. Layer 4: Capability Protocols

### 8.1 Pipes

Direct capability traffic multiplexes over one envelope kind: `PIPE_DATA` bodies are `PipeFrame{capability, payload}`, dispatched to the handler registered per capability type URI. This is the v1 datagram realization of the SPEC's pipe sketch. Every payload record is a protocol record with its schema in SPEC annex I.1: Java reads each through `CborCodec.fromWire`, and the clients read the ones they handle through their schema layers (§1.1; v0.1.31).

`CapabilityRuntime` hosts providers per group: `register(provider)` publishes the provider's advertisement first and stores and starts the provider only when discovery accepted it, so a refused provider never displaces a good one; `refreshTick()` reissues every hosted advertisement; `autoRefresh(period, executor)` schedules `refreshTick` at a period the host keeps below the 15-minute TTL, `close()` cancels it, and the default is off, with the Spring starter driving the tick from `card-refresh-millis` and the `AgentSpaces` facade's `refreshCards()` calling it alongside the cards.

### 8.2 Aggregate: push-sum, max-gossip, and histograms

`aspace:cap/aggregate` (`PushSumAggregate`) implements six operators (`Mode`: `SUM`, `AVG`, `COUNT`, `MIN`, `MAX`, `QUANTILE`) over one pipe frame, the union record `Frame{share?, extremum?, histogram?, roster?}` with exactly one field set: `Share{epochId, value, weight}` (push-sum: each tick the node halves its mass and sends half to one sampled member), `Extremum{epochId, max, value}` (max-gossip), `Histogram{epochId, lo, hi, buckets: double[]}` (a bucket vector pushed like a share), and `Roster{epochId, members: long[]}` (the union of 8-byte participant tokens, the first 8 bytes of `sha-256(PeerId)`). `AVG` is `value/weight`; `SUM` is the mean times the roster size; `COUNT` is the roster size; `MIN` and `MAX` are the extremum; `QUANTILE` (`Quantile{q, lo, hi, buckets}`, 100 buckets by default) interpolates the cumulative histogram and is exact within one bucket. Template mode (`start(epochId, mode, space, template, field)`) reads up to `TEMPLATE_READ_LIMIT` (10,000) local matches: `SUM` and `COUNT` contribute the local field total and match count plus the roster, `AVG` contributes `(Σfield, 1)` and runs a parallel epoch `<id>#n` for `(count, 1)` so the ratio is entry-weighted, `MIN` and `MAX` contribute the local extremum and nothing when nothing matches, and `QUANTILE` contributes one unit per match. Over a fully replicated space, template-mode `SUM` and `COUNT` count each entry once per replica; the other operators are replication-invariant. The advertisement carries `modes=sum,avg,count,min,max,quantile`. Every estimate converges in O(log N) rounds. The vote capability's approximate mode reuses `AVG` epochs under ids `vote:<voteId>:<option>` with contribution 1 or 0 per option. The v0.1.10 frame union replaced the bare `Share` frame and is not wire-compatible with pre-revision aggregate peers, of which none exist outside this repository.

### 8.3 Ordered log: Raft

`aspace:cap/ordered-log` is Raft's core over pipes: `Frame` is a union record of `RequestVote{term, candidate, lastLogIndex, lastLogTerm}`, `VoteReply{term, granted}`, `AppendEntries{term, leader, prevLogIndex, prevLogTerm, entries: [LogEntry{term, command}], leaderCommit}`, `AppendReply{term, follower, success, matchIndex}`, and `ClientSubmit{command}` (leader-hint forwarding for non-leaders). Elections use randomized timeouts counted in ticks; replication and commit follow the standard rules (commit on majority match within the leader's term); applied commands flow to listeners in commit order, which is what `ORDERED` takes consume (§7.7). A take command is `ClaimCommand{entryId, claim, holderKey, signature}`; the coordinator verifies the signature under `holderKey` against the claim's holder before accepting the commit, requires `claim.epoch == currentEpoch + 1`, and installs the claim on its replica through the attested `applyAuthorizedClaim` form with `holderKey` and `signature` unchanged (§7.6). It does not re-stamp the claim: commit order is carried by the epoch, and the replica treats a log-decided epoch as authoritative against gossip. The member set is fixed per log instance; reconfiguration means starting a new log, and single-server membership changes are future work. The leader lease is an advertisement: `RaftLog.describe` carries parameters `members`, `role` (`leader | follower | candidate`), `term`, and, for the leader only, `leaseUntil = issued + electionTimeout × tickPeriod` (the tick period defaults to one second). Consumers filter `providersOf(type)` for `role=leader`; a stale advertisement is superseded by a later issue or lapses with its TTL.

### 8.4 Vote: QUORUM

Proposals (`Proposal{proposalId, question, options, quorum}`) and ballots (`Ballot{proposalId, option, voter}`) are ordinary signed, leased entries in a vote space, so the space machinery supplies authentication, replication, and audit. The tally counts each voter's first-observed ballot once and skips ballots for options the proposal does not offer; the decision closes when distinct voters reach the proposal's quorum, and the winner is the option with the most votes, ties broken to the lexicographically first option so every replica closes identically. The counted voter follows the authorizer's granularity (v0.1.11): `granularity = authorizer.granularity(VOTE, space)`; for each ballot whose declared `voter` equals the authenticated issuer and whose option is on the proposal, skip it under `AGENT` unless `issued.attestation() == AGENT_ATTESTED`, skip it unless `authorizer.permits(issued.issuer(), VOTE, space)`, and count it under `key = granularity == AGENT ? issuer : issuer.peer()` once. `Decision` carries the `granularity` that produced it. `MembershipAuthorizer` holds per-peer and per-agent grants (`parsing(...)` accepts `peerId` and `peer/localName` strings, as the starter's `agentspaces.security.grants.*` do) and reports `AGENT` for an operation with at least one AgentId grant; `OidcAuthorizer` stays at `PEER` because a token binds to one PeerId. The golden vectors `vote_three_names_one_peer_delta_1..3` are three peer-signed ballots under three names from one peer; Java, Python (`agentspaces.vote.tally`), and TypeScript (`vote.ts`) tally them as one voter at `PEER` and none at `AGENT`. The electorate is a `Predicate<AgentId>` over the authenticated ballot issuer, evaluated at every tally: `VoteCapability.freshAgentCards(discovery)` is SPEC §8's rule (a ballot counts while an unexpired `AgentCard` for the issuer is in the group's ad-cache, so a decision can reopen when cards lapse), and `ANY_AUTHENTICATED_ISSUER` is the default for groups that publish no cards. Any member recomputes the tally from the space at any time; that recomputability is the audit property the flagships build on.

### 8.5 Gossip learning

`aspace:cap/gossip-learn` (`GossipLearner<M>`, with `GossipLearning` as the `double[]` facade) merges models through the `MergeableModel<M>` SPI: `merge` (commutative; an `IllegalArgumentException` abandons the exchange), `encode`, `decode`, and `name`, with `WeightAveraging` (element-wise mean over big-endian doubles) as the default. The wire frame is `Exchange{modelId, token, kind: OFFER | ACCEPT | BUSY, round, inline?, cid?}`: an encoding of at most 64 KiB travels `inline`, a larger one is stored in the group's `BlockExchange` and travels as its `cid`, and `contentId(model) = base58btc(sha-256(encode(model)))`. Each tick a node sends `OFFER` for each model to one sampled member and locks the model until the reply arrives or `PENDING_TIMEOUT_TICKS` (3) pass; an unlocked receiver merges and answers `ACCEPT` with its pre-merge snapshot, a locked receiver or non-participant answers `BUSY`, and the offerer merges the `ACCEPT` only when its token matches the outstanding offer, so both sides merge the same pair and the fleet sum of a commutative merge is conserved under any reordering; only a lost `ACCEPT` moves mass one-sidedly. `endEpoch(epoch, evaluate)` writes one `Evaluation{modelId, epoch, loss, contentId}` entry per local model into the metrics space configured with `Builder.metrics(space, lease)`. The advertisement carries `merge=<name>`, `exchange=offer-accept`, and `content=inline` or `content=inline,cid`. The v0.1.10 `Exchange` record replaced the earlier `{modelId, round, reply, params}` frame and is not wire-compatible with pre-revision peers, of which none exist outside this repository.

### 8.6 Semantic discovery

`aspace:cap/semantic-discovery` maintains an embedding index over the group's cards: AgentCards, AssetCards, ModelCards, AppCards, CapabilityAdvertisements, and SpaceAdvertisements. `SemanticDiscovery.textOf` gives the text each kind ranks by, and the TypeScript, Python, and Ruby clients index the same text; a ModelCard ranks by its `name`, `version`, `tasks`, `modality`, `engine`, and `licence`. The reference embedder is 256-dimension signed feature hashing over lowercased word tokens with L2 normalization, deterministic on every platform, so cosine ranking works with no model anywhere; richer embedders plug in behind the `Embedder` SPI without protocol changes. The SPI's `identity()` (default the class's simple name; `hashing` for the reference embedder, `spring-ai:<model>` for `agentspaces-springai`'s `SpringAiEmbedder`) and `normalized()` are advertised with `dimensions` as the capability's `embedder`, `dimensions`, and `normalized` parameters (v0.1.12). `remoteQuery` drops targets whose advertised embedder or dimensions differ, logging one warning per peer (`embedderMatches(peer)`; lifted with `requireMatchingEmbedder(false)`); the starter's `Embedder` bean (default `HashingEmbedder`) is the one every group's semantic discovery ranks with. Queries the local index cannot satisfy escalate through discovery (§6.3) with signatures re-verified on arrival.

### 8.7 Key wrap

`aspace:cap/key-wrap` distributes group content keys. The requester sends its raw X25519 public key inside a signed envelope; the holder authenticates the requester from the frame signature, applies its authorization policy, and replies with `WrappedKey{ephemeralPublicKey, sealed}`: a fresh X25519 keypair per wrap, RFC 7748 agreement with the recipient key, HKDF-HMAC-SHA-256 salted with both public keys in order followed by SHA-256 of the canonical CBOR `WrapBinding(group, holder, requester, nonce)`, under the info label `aspace-group-key-wrap-v2`, and AES-256-GCM over the 32-byte group key with the binding digest as associated data. Request nonces are `SecureRandom` longs; `GroupKeyDistributor` keeps each pending request with the holder it was sent to and drops a `KeyResponse` from any other sender. `GroupKeyWrap.wrap`/`unwrap` (v1, unbound) remain for compatibility tests only. Only the requester's decryption key opens the reply, so it may travel any path, relays included.

Rotation (SPEC §11a.3, v0.1.13): `serve(ring, …)` makes the distributor a ring holder; `KeyRequest` appends `epochs` and `KeyResponse` appends `keys`, a list of `EpochKey{epoch, rotator, cutover, proof, ephemeralPublicKey, sealed}`, each wrap bound with `WrapBinding`'s appended `epoch` and `rotator`. `rotate(PeerIdentity, cutover)` mints the next epoch with proof `EpochProof{rotatorKey, signature}` over CBOR `EpochCommitment{group, epoch, cutover, keyDigest}`; `vouched` verifies it for an authorized rotator before anything is installed. `follow(ring, discovery)` reads holders' `key-wrap` ads (`holder`, `epochs` — the newest 64 — `epoch`, `cutover`) on each capability tick, announces cutovers from authorized rotators, and fetches missing epochs in the background; `autoRotate(rotator, every, cutoverDelay)` rotates on time. `RingStore` persists a ring at `<keystore>/content-keys/<group>.ring`, each key wrapped to the peer's X25519 key (`FileKeystore.encryptionKeys`, `peer-x25519.key`) under binding `("aspace-content-key-ring-v1", group, epoch, rotator)`, saved on every install. Per-agent wrap (SPEC §11a.2a): `requestAs(peer, agent, holder, epochs, timeout)` sends `KeyRequest.agent = AgentRequest{agent, certificate, peerKey}` with the agent's certified X25519 key; the holder checks `PeerId.fromPublicKey(peerKey) == from`, the agent's peer, `AgentCertificates.verifyAt(cert, peerKey, agent, now, now)`, a certified `encryptionPublicKey`, `refuseAgents`, the group's `RevocationView` for the agent and its key, and the per-agent policy, then seals to the certified key under `WrapBinding.agent`; the agent opens with `AgentIdentity.agreeEncryption`. Under Spring Boot each group with a `content-key` gets one ring shared by its spaces; the key-wrap capability serves and follows it; `agentspaces.groups[].content-key-rotation` sets `rotate-every` (unset: never rotates on its own), `cutover-delay` (unset: two gossip periods plus 30s), and `writer-grace` (1h); the ring persists when `agentspaces.keystore` is set; and `GroupContext.rotateContentKey(cutoverDelay)` rotates on demand. Startup fails when `rotate-every` is set without a content key, with key-wrap off, or on a peer that may not rotate.

## 9. Bindings and Gateways

### 9.1 Schema names

Entry types are named `<fully.qualified.ClassName>#v1` (`SimpleSchemaRegistry`). Cross-peer type identity is by this name, so fleet members share domain types by sharing the class (the wire itself is language-neutral CBOR; the non-JVM clients map the same names to their own structures). Writer/reader schema evolution stays an open design question (SPEC §14). Since v0.1.14 the registry is shared: `AgentBinder.schemas(SchemaRegistry)`, `AgentSpaces.schemaRegistry(...)`, and `GroupContext.schemaRegistry(...)` give the binder the registry its spaces were built with (`ReplicatedSpace.Builder.schemaRegistry`, `LocalSpace.Builder.schemaRegistry`; the Spring starter applies a `SchemaRegistry` bean to both), so a card's `consumes`, `produces`, `spaceBindings`, and actions carry the same names as the records; `RemoteActions` resolves a card name through the registry's `classFor` first and falls back to the class-name rule only for names without `:` or `/`. `NamespaceSchemaRegistry.of(packageToNamespace)` names classes under mapped packages `<namespace><SimpleName>` and delegates everything else to the default rule, so the reserved types (`SpaceCredential`, the vote records, `JoinTicket`) keep their names everywhere.

### 9.2 Annotations to protocol behavior

`@SpaceTake` runs the leased-take loop of §7.7 with the method parameter type as the template, taking exactly one parameter; a normal return completes with the result under `resultLease` into the take space or the named `resultSpace`; an exception skips `complete`, and the lease lapse is the crash idiom. `@SpaceNotify` registers a leased subscription; delivery is deduplicated per entry id against a bounded per-subscription set (4,096 ids), invoked on a dedicated virtual thread, a non-void return is written as a new entry, and the binder renews the subscription at half-lease on a virtual thread while the agent stays bound. `@BidFunction` installs the AUCTION bid function, one per space per peer; the binder refuses a second, naming both agents, before the space's own single-assignment setter would. `@SpaceRef` injects the space handle at bind time. Since v0.1.14: `tags = {"k=v", "k"}` on `@SpaceTake`, `@SpaceNotify`, and `@OrderedTake` compiles to `Template.whereTag`/`hasTag` conditions on the method's template, built once at bind time (a malformed filter is refused naming the method); every binding's return goes through one dispatch (`null` or void completes and writes nothing, `Contribution` goes to the aggregate, `Tagged` is unwrapped and written through `complete(taken, entry, lease, tags)` for a same-space take result or `write(entry, lease, tags)` otherwise, a `Tagged` `Contribution` is refused), and a method returning `Tagged<X>` declares `X` on its card. `@SpaceJoin(space, key, parts, mode, within, maxOpen, lease, ticketLease, takeLease, pollTimeout, resultSpace, resultLease, name)` with `@Part(value, space, key, keyTag, tags, optional)` builds a `JoinBinding`: one subscription per part (filtered template, WRITTEN and REAPPEARED events), per-key state seeded with `readAllEntries` per part on start and re-seeded for a key met for the first time (so a key forgotten after `within` or evicted beyond `maxOpen` is found again from what the space holds), firing on a virtual thread with a `Joined` bag (parts re-read by key, newest by issue stamp first; `get` throws when absent, `find` is for optional parts). `LOCAL` keeps a bounded set of fired keys; `LEASED` writes `JoinTicket(join, key)` tagged `join`/`key` into the join's space, withdraws it when an older live ticket for the key exists, and serves tickets through `Space.take` (a failed firing lets the ticket's TAKE lease lapse); `ORDERED` serves them through `OrderedTakes.take` and registers `OrderedTakes.onCommitted(listener)` (new, called on the apply path for every authentic committed claim in log order, after the claim is installed, or without installing it when this member already holds that generation through gossip, which `ReplicatedSpace.verifiesAuthorizedClaim` checks) to record, per key, the entry id of the first committed ticket claim as every member sees it, so only that ticket fires and later tickets for the key are completed without firing; a committed claim whose record has not replicated yet is resolved in commit order once it has (a completed ticket still answers from its tombstone), and a taker whose key is still undecided after half its TAKE lease neither fires nor completes, so the ticket reappears and is decided with the record in hand. The join's default name is `<agent name>.<method>`, so joiners of one class on several peers share tickets. The card declares one `CardAction` of kind `join` (`CardAction.JOIN`, not invocable). `Motion`: `dispatch` gains a branch after `Contribution` that completes a take and then calls `move(motion, handle, site, label, defaultVoteSpace)`, which resolves the vote space (`motion.space()`, else the caller's default, else the sole registered one), reads `proposal(id)` through `voteFor(identity, space)` and skips when present, else `propose`s; `action(...)` refuses a declared `Motion` return with no vote registered and a declared `Contribution` return with no aggregate, and a declared `Motion` return produces `VoteCapability.Proposal` on the card, bound to the sole vote space when there is one; `VoteClient.propose(Motion)` is the same idempotent open without the binder. `@Propose(space, group, vote, prefix, key[], keyTag, options[], quorum, lease, subscriptionLease, tags[], description)` binds through `watch(...)`, the leased, entry-deduplicated subscription `@SpaceNotify` now also uses; per WRITTEN cue it derives `prefix + Keys.keyOf(cue, key accessors)` (fields joined by `:`) or `prefix + tags[keyTag]`, skips a keyless cue, gates the method on a bounded per-binding set of opened ids (so several cues of one proposal invoke the method once), reads `proposal(id)` through `voteFor` and skips when present, invokes on a virtual thread, and opens a `String` return with the annotation's options, quorum, and lease, a `Motion` return through `move` with the annotation's vote space as default, and nothing for `null` (releasing the id so a later cue may ask); a failed open releases the id and logs; bind-time refusals name the attribute (fewer than two options, non-positive quorum, both or neither key and keyTag unless the method returns `Motion`, an unknown key field, a malformed filter, a return type other than `String`, `Motion`, or `void`, an unregistered vote space). The card declares one `CardAction` of kind `propose` (`CardAction.PROPOSE`, not invocable) consuming the cue and producing the `Proposal`. The Layer 4 annotations (2026-09-26): `@Ballot` subscribes to `VoteCapability.Proposal` writes in the named vote space (prefix-filtered), deduplicates per proposal, invokes on a virtual thread, and casts the returned option through the vote registered for that space (`binder.vote(space, vote)`, `GroupContext.vote(...)`, or `provide(VoteCapability)`), over the agent's view of the space when the agent is subordinate (`VoteCapability.as(view, voter)`); `@OnDecision` uses `VoteCapability.onDecision(proposals, listener, lease)`, which watches `Ballot` and `Proposal` writes and recomputes `decision()` per proposal, firing once, and writes a returned value to `resultSpace` (default the vote space); `@OrderedTake` runs `@SpaceTake`'s loop over the `OrderedTakes` registered for the space (`binder.ordered(space, coordinator)`, `GroupContext.ordered(...)`, which also provides the coordinator's `RaftLog`), refusing at bind time a coordinator whose holder is not the space handle's writer, and treating a `RuntimeException` from `take` (an election in flight) as a resubmit on the next poll; `@CapabilityRef` injects a registered client (`binder.client(type, instance)`) or one the group's typed-client lookup resolves; a `Contribution` return from any bound method calls `PushSumAggregate.start(epochId, value)` on the registered aggregate (`binder.aggregate(...)`, `provide(PushSumAggregate)`). `OrderedTakes.over(pipes, codec, identity, name, members, clock, seed, space)` builds the log and coordinator together; `AggregateClient.awaitEstimate(epoch, timeout)` replaces the removed manual `tick()`; `SemanticClient` is the third typed client. Space names are optional when the binder registers exactly one space; durations parse Spring-style simple forms and ISO-8601. The class-level `@AgentSpec` resolves through one level of meta-annotation, which is how the Spring `@SpaceAgent` stereotype and application-defined stereotypes work.

The workflow verbs (v0.1.14) ride the same binder paths. `Entries` (`of(Object...)`, `of(List)`, `elements()`) is one more branch of `dispatch`: a take is completed once with no result, then each element is dispatched on the write path, so a `Tagged`, `Motion`, or `Contribution` element behaves as its own return would, and a nested `Entries` throws; `producedTypes(method, declaredProduces)` derives a card action's produced names from a `Motion` (`Proposal`), a `Tagged<X>` (`X`), a sealed return (its permitted subclasses), or the annotation's `produces` list for an `Entries` or `Object` return. `where` is parsed by `templateFor(type, tags, where, site)` into `Template.where(field, Matchers.predicate(v -> negated != value.equals(String.valueOf(v))))` once at bind time, after checking the field is a record component of the parameter type. `@SpaceNotify.on` is the set of `SpaceEvent.Kind` the shared `watch` helper passes to its listener; the deduplication key is the entry id alone for a single-kind watch and `entryId:kind` for several, so one entry's write and lapse are two deliveries and a redelivered write is one. The gather lives in `JoinBinding`: a `PartSpec` carries `atLeast` and the `countedBy` type and field; a `KeyState` keeps the entry ids seen per part (so a redelivery counts once) and the counts declared by the parts that landed, and is complete when every required part meets its `atLeast` or declared count; `settle` is judged on the keep thread from the key's last-arrival stamp; the firing re-reads every part by key (`READ_LIMIT` 256) and `Joined.all` returns them newest first. `@OnEstimate` registers `PushSumAggregate.onEstimate(id -> id.startsWith(prefix), Settle.after(settleTicks, tolerance), listener)` on the binder's aggregate at bind time (refused without one), the capability evaluates every watch at the end of `tick()` over `knownEpochs()` and fires each at most once per epoch on a virtual thread, and the listener invokes the method with the `Estimate` and dispatches its return as any other; the card action's kind is `on-estimate` and `AgentSpaces.namedGroups` honours the annotation's `group`.


A ticket's taker is not the member that saw the key complete (2026-10-08, the ordered join stress investigation). In `LEASED` and `ORDERED` the ticket is written by whoever saw every part and taken by whoever wins the claim, and the winner may not hold every part yet; `JoinBinding.fireWhenPartsReadable` waits up to the lesser of half the take lease and five seconds for them, and when they never come the taker forgets the key and leaves the ticket to lapse by its lease rather than completing it, so the ticket reappears for a member that holds the parts and the key is never lost to replication lag. `LOCAL` likewise forgets a key that fired nothing.

`@SpaceReduce` (v0.1.15) is the persistent accumulator. The binder resolves the element type and the accumulator type from the method's two parameters, refuses any other shape, a return other than the accumulator type, `Tagged`, or `Entries`, a `key` the element lacks, a `name` shared with a `@SpaceJoin` on the agent, `ORDERED` without a coordinator, and an `accumulatorLease` below the take lease. `ReduceBinding` sweeps the available elements on bind and every `pollTimeout`, subscribes to the element template for `WRITTEN` and `REAPPEARED`, and drains one key at a time: `KeyTickets.request(key)` writes a `JoinTicket` named for the reduce unless one is visible (withdrawing the younger of two written in one instant), the ticket is taken under `lease` (through the coordinator in `ORDERED`), a reducer whose ticket is not the key's oldest live one completes it bare and backs off (`LEASED`: the live tickets as the space's own events show them, so a claimed ticket still counts; `ORDERED`: `KeyTickets.earliestLive`, the first committed ticket claim for the key whose record is still present), and the holder, renewing the ticket's take lease before every step and stopping when a renewal fails (the ticket is the lock only while its lease holds; one step must fit inside it), then takes one element at a time, reads the newest accumulator (`Reductions.current`: the highest `steps` tag among the visible ones), invokes the method, completes the element with the new accumulator tagged `reduce`, `key`, `steps` under `accumulatorLease`, retires the predecessor (a cancel through its own handle, else a take and a bare completion), and dispatches a fork's other elements. A method that throws ends the drain and the element reappears by its lease; a `null` return completes the element bare. The ticket is completed after the drain, so a later element raises a new one. `KeyTickets` is the ticket code extracted from `JoinBinding`, which now rides it too. The card action has kind `reduce`, outside `INVOCABLE`.

The `group` attribute on `@SpaceTake`, `@SpaceNotify`, `@BidFunction`, and `@SpaceRef` (v0.1.10) scopes a binding: `""` means every group whose registered spaces satisfy it, and `AgentSpaces.bind(bean)` binds into each; a name means that group only; a named-but-unjoined group or an unsatisfiable binding throws `IllegalArgumentException`. A `@SpaceRef` without a group is injected by every binding group, last wins. Binding publishes one `AgentCard` per bound group, all refreshed together by `refreshCards()`, whose consumed and produced schema names come from the bound method signatures and whose `spaceBindings` map each consumed schema to the space its `@SpaceTake` (or, failing that, `@SpaceNotify`) names. `EmbabelBinder` fills bindings the same way, skips beans the space binder already handles (`AgentBinder.isAgentType`), and publishes through `AgentBinder.adopt(card)` so Embabel-derived cards are refreshed too.

Capability clients come from the `CapabilityClientFactory<C>` SPI (`ServiceLoader` plus `AgentSpaces.clientFactory`); `spaces.group(g).capability(VoteClient.class)` caches one client per group and type. `VoteClient` resolves a local `VoteCapability` when one is registered and otherwise builds over the vote space a discovered advertisement's `space:<name>` binding names, which requires the group to have registered that space with a writer identity; `AggregateClient` wraps or creates a `PushSumAggregate` over the group's `CapabilityPipes`. A `@ProvidesCapability` bean implementing `CapabilityProvider` is registered on the named group's `CapabilityRuntime`, or every group's when unnamed.

### 9.3 Remote actions

The planner bridge (SPEC §10.6) turns foreign AgentCards into invocable actions. Card schema names resolve to local classes by stripping `#v1` and loading the class; one action exists per foreign card and resolvable (consumed, produced) pair. The input's space resolves in a fixed precedence: an explicit route on the registry, then the card's `spaceBindings` entry for the consumed schema when it names a locally registered space, then the sole registered space; the result is awaited in the input's space unless a `resultsIn` route names another. Invocation subscribes to the result type first, snapshots a multiset baseline of existing results, writes the input entry under a 10-minute default lease into the routed space, and then accepts the first result that arrives (by event, or by poll for content-addressed results) passing the correlation predicate; the default correlation requires equality of every record component name the input and candidate share. A timeout returns empty with the input entry still leased in the space. The Embabel adapter generates an `@Agent`-annotated class with one typed `@Action` method per action (ByteBuddy), maps card goals to `@AchievesGoal`, and deploys reflectively. `EmbabelRemoteActionsDeployer` polls the registry on a virtual thread and redeploys a fresh generation whenever the action set changes (first cards, a new capability, an expired card); a refresh that changes only issue times does not redeploy; the platform surface has no undeploy, so a vanished action stays registered until restart and fails by timeout when invoked. The Spring starter wraps the deployer in a `SmartLifecycle` over the `AgentPlatform` bean (`agentspaces.embabel.auto-deploy`, `deploy-poll-millis`).

### 9.4 The A2A gateway

The gateway serves discovery at `/.well-known/agent-card.json` plus per-agent cards translated mechanically from AgentCards (one skill per invocable declared action, with the action's own description and schemas and the agent's goals as `goal:` tags, when the card declares actions; otherwise one skill per goal), and speaks A2A JSON-RPC over HTTP: `message/send` writes `A2aTaskEntry{taskId, agent, text}` under the task lease; `tasks/get` derives task state from space semantics (a present entry is `submitted`, a consumed one `working`, a result `completed`, a withdrawn one `canceled`; an entry that vanished untaken reads `working` until the write-lease deadline recorded at submission and `failed` after it, with `status.message` "no worker took the task before its lease expired" in the agent role); `tasks/cancel` withdraws via the entry handle; `message/stream` and `tasks/resubscribe` stream state transitions over SSE, with `failed` terminal (`final: true`) for SSE and push alike; `tasks/pushNotificationConfig/*` manages webhook push. `TaskStatus` carries an optional `message`, omitted unless present. Card URLs are built from `A2aGateway.externalBaseUrl(url)` when set (trailing slash stripped, blank refused) and otherwise from the bound address: the hostname when bound by name, the literal address when bound by address, `localhost` for a wildcard bind; deployments off loopback or behind a proxy set it. The binding records each task's write-lease deadline at submission and compares against it in `tasks/get` on an injected `InstantSource` (default `InstantSource.system()`), which deployments and tests set to the clock the space runs on, so the binding's view of a lapsed lease agrees with the space's and the lapsed-task tests drive a `TestClock` instead of sleeping. Fleet workers serve A2A tasks by taking `A2aTaskEntry` and completing with `A2aTaskResult{taskId, text}`; the explicit `taskId` field is the correlation key on this boundary, in contrast to §9.3's shared-field convention over domain types.

*Bearer principals (SPEC §12, v0.1.11).* The gateway and the fleet console's command routes gate their HTTP edge with one model, `BearerAuthenticator` (`agentspaces-api`, `api.security`): `Optional<Principal> authenticate(String bearerToken)` with `Principal(String subject, Set<String> scopes)` and `Principal.permitsScope(scope)`, which passes an empty scope set and otherwise requires the scope to be present. `BearerAuthenticator.staticToken(token, subject)` compares in constant time and yields the fixed subject with no scopes. `BearerJwtValidator` (`agentspaces-auth-oidc`), built with `fromJwks(issuer, audience, jwksUrl)`, validates every request with the Nimbus processor it shares with `OidcAuthorizer` through the package-private `JwtProcessors`, so the two cannot drift on accepted algorithms or issuer and audience matching; it requires `exp`, `sub`, and a non-blank `scope` claim, treats `agentspaces_peer` as optional because operators are humans, and yields empty for an expired, wrong-audience, wrong-issuer, rogue-key, blank-scope, or non-JWT token. On the gateway, `A2aGateway.bearer(BearerAuthenticator)` gates every JSON-RPC method, `operatorToken(String)` delegates to `staticToken(token, "operator")`, and `requiredScope(String)` defaults to `A2aGateway.CLIENT_SCOPE`, `aspace:a2a:client`. On the console, `FleetConsoleServer.Builder.commandAndControl(commander, BearerAuthenticator)` gates `POST /api/v1/commands/*`, the string overload delegates to `staticToken(token, "operator")`, the required scope defaults to `FleetConsoleServer.OPERATE_SCOPE`, `aspace:console:operate`, and the token arrives as `Authorization: Bearer` or, for the static gate, `X-Console-Token`. On both surfaces a token the authenticator refuses is `401` with `WWW-Authenticate: Bearer`, a scoped principal without the required scope is `403`, discovery GETs stay open, and the audited operator is `principal.subject()`: the console drops the request body's `operator` field from attribution, so the static gate audits every holder as `operator` and the JWT gate audits the token's `sub`. Without any gate the gateway's RPC surface is open, which is acceptable only behind its default loopback bind. Under Spring Boot the console takes the static `agentspaces.console.command.token` when set; otherwise, when `agentspaces.security.oidc.{issuer, audience, jwks-url}` are configured, it builds the JWT validator and requires `agentspaces.console.command.required-scope` (default `aspace:console:operate`). Under Spring Boot (v0.1.13) `AgentSpacesA2aAutoConfiguration` builds the gateway when `agentspaces.a2a.enabled=true` and `agentspaces-a2a` is on the classpath (the starter brings it): cards from `spaces.group(group).discovery()`, an `A2aTaskBinding` over `agentspaces.a2a.space` with `task-lease-millis` (600000) and `result-lease-millis` (3600000) on the group's clock, `external-base-url`, and `allowed-webhook-hosts`. The gate follows the console's rule: a non-blank `agentspaces.a2a.token` wins; otherwise `security.oidc.*` selects the JWT validator requiring `agentspaces.a2a.required-scope` (default `aspace:a2a:client`); otherwise the gateway is ungated and startup fails unless `agentspaces.a2a.bind` (default `127.0.0.1`) is a loopback address. `AgentSpacesA2aLifecycle` listens on `bind:port` (default port 7594) after the fabric starts and closes first. `group` defaults to the first configured group and `fleet-name` to the group's name. The facade, the authorizers, every starter-built space, and the task binding share the `InstantSource` bean `agentSpacesClock`, which an application or test may replace.

## 10. Implementing a Wire-Compatible Client

A new client implements, in order: the wire encoding of SPEC §9.1 for the structures in §3 and §7, fields in declared order, with the item rules, the record rules, and the canonical-bytes check on every carrier it decodes (annex I of the SPEC lists the schemas and the vectors); Ed25519 signing and verification with raw 32-byte keys; the id derivations of §1.3; HLC stamps with the acceptable-stamp grammar of SPEC §9, the drift clamp one millisecond inside the cap, the logical limit, and the carry of §1.4 (all four as v0.1.30 states them), refusing a remote stamp that is not acceptable at every merge, ordering, and deduplication point the client has, and counting the refusal (the clients keep no strikes); frame encoding, verification (including the `ver = 3` check and the `to` binding), dispatch, and the reserved streams (`peers`, `ads`, `space:<name>`); the founding document of §1.3 and the join-by-GroupID handshake (send an unaddressed `GROUP_AD_WANT`, verify the `GROUP_AD` answer with the four checks of SPEC §5.1, and introduce yourself only when the document derives to the GroupID you asked for); the record and state signature views of §7.2 and §7.4, verifying both before merging; the claim lattice of §7.6 byte-for-byte (merge must return an input); and the LEASE_RACE settle discipline of §7.7. The golden vectors (§1.5) pin every structure above exactly, including the v0.1.10 additions: the founding fields, signature, and document, the `GROUP_AD_WANT` and `GROUP_AD` envelopes and frames, two hostile `GROUP_AD` answers (wrong id, forged signature) that every implementation must refuse, the AgentCard with space bindings and its stored form, the SpaceAdvertisement with admission and replication, the four aggregate frame variants including a negative int64 roster token, the three gossip-learn exchange kinds with a content id, and the wire version. The Python client (`agentspaces-python/`) is the reference second implementation, the TypeScript client the third, and the trilingual demo exercises a mixed fleet racing takes under the lattice. Regenerating the vectors is documented in `docs/BUILD-ENVIRONMENTS.md`; the generator reloads the golden key from the existing file, so a regeneration adds vectors without changing existing bytes.

### 10.0a Join credentials and the beacon document (v0.1.18 addenda)

*Delegated join credential.* Both credential forms travel under the `aspace:join` resource hint as strings. The founder-issued form is base64 of the CBOR map `Credential{founderKey: bytes(32), signature: bytes(64)}` where the signature is over the CBOR of `CredentialView{candidate: PeerId string, group: GroupId string}`. The delegated form is the string `d1:` followed by base64 of the CBOR map `DelegatedCredential{delegation: Delegation, signature: bytes(64)}`, where `Delegation{founderKey: bytes(32), inviteKey: bytes(32), group: GroupId string, notAfterMillis: int, label: string, signature: bytes(64)}` carries the founder's signature over the CBOR of `DelegationView{inviteKey, group, notAfterMillis, label}` and the outer signature is the invite key's over the same `CredentialView` as above. Maps are Jackson's canonical CBOR as everywhere in this document, fields in the declared order. A `JOIN_CREDENTIAL` revocation's hash is the SHA-256 of the decoded bytes: of the credential (one holder) or of the delegation (every holder). The golden vector `agentspaces-bootstrap-social/golden/social-golden.json` fixes every byte.

*Beacon document.* JSON, fields in the order `v, issuer, issuerKey, issued, ttl, groups, signature`; a group in the order `name, id, founding, seeds, wire, multicast, parameters, invite`; a seed in the order `transport, address, priority`; null fields of the document and of a group omitted, a null seed field or map value written `null`; the keys of `wire` and `parameters` sorted by UTF-16 code units (Jackson's `ORDER_MAP_ENTRIES_BY_KEYS`); no whitespace; strings escaped as Jackson escapes them. The signature is the issuer's Ed25519 signature over `canonicalBytes()`, the serialisation without the `signature` field as Jackson's byte writer writes it, which escapes each character past U+FFFF as two upper-case `\uXXXX` surrogate escapes; the served document (`toBytes()`) holds such a character as UTF-8. `issuerKey` (base64 raw key) must hash to `issuer`. Since v0.1.31 `BeaconDocument.parse` refuses a document that carries a signature unless its bytes equal `toBytes()` of the document it parsed and `signature` and `issuerKey` are each the padded standard base64 of their bytes (SPEC §9.1), and the clients' readers (Python `beacon.parse_document`, TypeScript `parseBeaconDocument`, Ruby `Beacon.parse_document`) refuse the same documents. A reader ignores unknown fields of an unsigned document alone, and since SPEC v0.1.32 (§9.3) it refuses a document, signed or not, whose named field holds another type than Java's: `BeaconDocument.parse` reads with every Jackson coercion off, so a number, a boolean, or text never fills a field of another type. Served at `/.well-known/agentspaces/beacon.json` and, at a social beacon, under `/j/<code>`.

*Locators.* A node asks a `BeaconLocator` with the configured group name, the GroupId when known, and the schemes it dials; the answer's endpoints are dialed through the non-member path of §3, a GroupId claim is honoured only from locators the operator names, a founding is verified as any learned founding advertisement. The re-ask while a view is empty is paced by the locator's `LocatePolicy` (floor 30 s, ceiling 10 min by default) and never reaches the wire except as the dials it causes.

### 10.1 Residency of a JavaScript host

A JavaScript client declares a residency, judged at bind time against each verb: `visitor` (a page: watches, takes, `@spaceNotify`, `@orderedTake` as a Raft client, LOCAL joins, MAJORITY_GOSSIP shares), `resident` (a SharedWorker or Worker holding a Web Lock: adds the keeper duties — LEASED and ORDERED joins and `@spaceReduce`), `cell` (a Durable Object: keeper and connector duties), `service` (a Node process: every duty, including the Raft voter, the listeners, and relay). An unknown class ranks as `visitor`. A host reports its class in its advertisement's resource hints as `js.residency`; peers never trust the hint for safety. A service host whose tick drifts beyond twice its period three times running drops to visitor duties (voters suspend, leases lapse) and regains its class after sixty seconds of cadence.

### 10.2 The Raft messages on the wire

A voter in another language encodes the `aspace:cap/ordered-log` pipe payload as the Java `RaftMessages.Frame` union — a map with the keys `requestVote`, `voteReply`, `appendEntries`, `appendReply`, `clientSubmit`, exactly one non-null — with `RequestVote(term, candidate, lastLogIndex, lastLogTerm)`, `VoteReply(term, granted)`, `AppendEntries(term, leader, prevLogIndex, prevLogTerm, entries[{term, command}], leaderCommit)`, `AppendReply(term, follower, success, matchIndex)`, and `ClientSubmit(command)`, pinned by the golden vectors `raft_*`. Membership is fixed at construction and identical on every member; a voter writes its term and vote before a `VoteReply` and its entries before an `AppendReply` (`LogStore` in Java and `@agentspaces/ordered`). A non-member may send `ClientSubmit` alone, admitted under the `RAFT_CLIENT` authorizer operation within a per-sender rate. The committed `ClaimCommand` installs its claim only at `epoch == committed + 1`, as `OrderedTakes.onCommand` decides.

### 10.3 Serving anti-entropy from another language

A client that accepts connections answers a `DIGEST` with the encodings of §5.4, §6.2, and §7: a space digest is one `e:<entryId>=<stateHash>` line per entry and one `c:<entryId>=<claimHash>` per claim in key order, where `stateHash` is `Integer.toHexString(Objects.hash(adds, removes, lease.stamp, completed))` over the record components and `claimHash` is `epoch:stamp:bid:expiresAtMillis` with the bid as `Double.toString` prints it; the vectors `space_state_hash`, `space_claim_hash`, and `java_double_strings` pin the arithmetic. The ad digest is 32 bytes of SHA-256 over the `<id>=<issuedMillis>` lines followed by the lines; the revocation digests are `r:<peer>=<sha256>` and `c:<kind>:<target>=<sha256>` lines.

## 11. Where the Implementation Trails the Design

Recorded plainly, so this document never overstates. The v0.1.10 reconciliation closed the deviations earlier revisions of this section carried: tombstone garbage collection now runs under the §7.3 rule, `ConsistencyHint.FRESH` exists (§7.7), reads of content-addressed entries no longer block (§7.8), the SPEC §9 kind list matches §3.1, and the group advertisement is verified at join. The v0.1.11 authorization pass closed three more: the `Authorizer` arbitrates every enforcement point (§4) in place of construction-time member lists and hard-coded PeerIds, `CREDENTIAL` and `AUTHORIZER` space admission ship (§7.10), and the console and A2A gateway validate bearer principals by subject and scope (§9.4). The accepted security risks are recorded in SPEC §11/§11a.3: unauthenticated push-sum and gossip-learn values, lying AUCTION bidders, the plaintext `type`/`tags` metadata under group encryption, and the per-key GCM nonce ceiling, which `GroupKey` now counts and enforces (warning at 2^31 seals, refusal past 2^32).

What still trails the design: garbage collection of a read-only space after its longest entry lease (SPEC §7.5; tombstones inside it are collected, the space object is not); Raft membership change, single-server or joint (§8.3); and the real UDP multicast carrier, which ships but is exercised only by hand, the suite driving the beacon through an in-memory carrier (§5.2). The WebSocket and HTTP-exchange bindings shipped in v0.1.21 (`agentspaces-transport-http`), with the TypeScript dialers, the browser member, and the Node service host of the same design; the `webrtc` binding of that design is recorded in §5.5 as it lands. QUIC's pipe-per-stream refinement and the DTLS binding's lanes, datagram mode, congestion control, and DTLS 1.3 default are future work. CROSS_INHIBITION voting and the standalone `task-auction` capability remain planned, with the AUCTION strategy as the shipped surface.

Deferred in v0.1.13 and recorded with the revision: `content-key-rotation.prune-unreferenced` is not built, so a `GroupKeyRing` keeps every epoch up to 4096; push-on-rotation is not built, so members learn a new epoch by following holders' `key-wrap` advertisements and pulling it, within a tick or two; a `VoteCapability` recount excludes ballots of revoked agents and peers but not of a revoked `AGENT_KEY`, because a ballot carries no signing key, so a key revocation stops only new ballots, at merge; an `X509_LEAF` compromise cuts every link presenting the leaf but does not escalate automatically to a `PEER` revocation of the CN's PeerID, so the founder revokes the peer; CA-rooted peer revocation and decryption of sealed spaces are Java-only, the Python and TypeScript clients ignoring evidence-rooted records and reading no sealed payloads; and `CaRootedRevocationFabricTest` runs over TLS alone, with no QUIC variant (`QuicCaModeFabricTest` covers connection-level CRL refusal over QUIC).

Added with SPEC v0.1.23 (the large-data revision, 2026-10-27): the Java reference implements content roots, the manifest and holding records, the content-swarm and relay-signal capabilities, relay paths, and the escalation seam; the TypeScript and Python clients implement none of them yet (they skip a `b` reference as they skip an absent block, and the TypeScript relay forwards one hop only), the golden vectors of SPEC annex G are not yet generated, and sealed pieces are stored only by key holders.

Recorded with SPEC v0.1.31 (2026-11-08): Java, Python, TypeScript, and Ruby implement the canonical stamp grammar and the stamp item under its shortest length header, the wire encoding of SPEC §9.1 with the canonical-bytes check on every carrier and the exact types of application big numbers, the validated local node, the refusals with `signedAt` judged like `issued` and `leaseStamp` after the signature and revocation checks and under the far-future rule, the advisory head stamp with its fallback and `headsIgnored`, the deferral of far-future states and claims for peer-signed and agent-signed carriers alike with each offer judged afresh, the seven counters, the counting keyed on signed content under caches that keep the 4096 most recently offered keys, a claim's signature over its `TakeClaim` encoding with a claim out of that order undecodable, Java's claim checks, the bounded claim map, the shared base of a ref merge, the drift cap, the carry, the frame-filter order, and the skew margin of SPEC §4.2, §7.3, §7.4, §9, and annex H. Java and TypeScript acknowledge a refused state in their space digests, a revoked actor's state and claim included; the Python and Ruby clients pull with empty digests and acknowledge nothing. The HLC conformance harness ran all four over 649 rows on 2026-11-08, and 646 agree with no disagreement; the three left report behaviour with no verdict to compare. It also ran 86 round-seven rows, the pipe records and the beacon vectors, whose 240 client verdicts match Java's, none differing and 18 without a reader (SPEC §9.3). Round seven closed the bignum cap, the pipe payload schemas, the pass-through of `undecodableEntries` in a console's read-only and routing `Space` wrappers, the TypeScript WebRTC signal reader, the long stamp, and the `Map` defect of TypeScript's `cbor.dumps`, and it made a signed beacon document arrive as its canonical JSON. Round seven left two gaps, and SPEC v0.1.32 §9.3 records both closed on 2026-11-09: Java reads the content swarm's messages through `fromWire` since 2026-11-09, and every implementation refuses a beacon document, signed or not, whose named field holds another type than Java's (the vectors `beacon-32` to `beacon-40`). No client reads the gossip learner's exchanges, and Python and Ruby read no WebRTC signal. The AgentSpaces Rust team owns the Rust peer, which keeps a stamp with a counter above 65536 out of its clock, yet still dispatches the frame and folds the state or the claim that carries one. It has not adopted the carry, the clamp one millisecond inside the ceiling, the node rule of the grammar, the `signedAt` judgement, the deferral, the certificate rule for records, claims, and states, the counters, or the skew margin; it already refuses a claim whose map arrives out of `TakeClaim` order, as v0.1.31 requires, and as its source read late on 2026-11-08 its network decoder applies the item rules S1 to S12, so it refuses a head longer than its argument needs and reads Jackson's text chunks and tags 2, 3, and 4. A read-only reading for round seven (v0.1.31) found that it also refuses a bignum past 1000 bytes, that it bounds neither a stamp's length nor a node's, that its aggregate reader takes an integer where a double belongs and ignores an unknown key, and that its beacon reader verifies a signature over a re-encoding and ignores unknown members. Whether it applies the record rules and the canonical-bytes check to every record stays for the Rust team to confirm, and that team has the exact changes. Until it ships them, a Rust peer can hold states and claims the other implementations refuse. The bound on recounts trails the promise of one count per distinct state or claim: it holds for the 4096 most recently offered refused or deferred keys (§7.5).

Recorded with SPEC v0.1.32 for PDT 2 (built 2026-11-08 and 09): Java implements every normative rule of SPEC §6.1a.6, §7.1's store entries, §8's level-2 forms, and annex H's PDT 2 paragraphs; Python and TypeScript implement level 2 and advertise `pdt` = `"2"`, and Ruby reads the level-2 trees and heads at level 1 (SPEC §9.3). What still trails the design: chunk-group picks, which `TreeServer` answers as missing; VCDIFF frames, refused by name; structured nodes named by BLAKE3; the read half of verified BLAKE3 windows on the flat swarm, since its `fetch` verifies no range through a `bo` node set; the Merkle Search Tree boundary and the ClojureScript adapter; a late joiner's reconcile of its version-graph nodes; pushed against pulled bytes on the console; the console's `StorePanel`; the holding's `cost` and cold tiering; the browser worker's lazy `db` reader; the challenge deadline's eight round trips, since `Stores` waits a configured 2 s; a backoff per chain node in Java's and Ruby's version-graph walks, which stop at their first failed batch; the Spring and Micronaut properties `agentspaces.pdt.push.*`, `agentspaces.pdt.blobs.deltas`, and `agentspaces.store.reconcile-every`; and the Rust port, which the Rust team owns.

Built with SPEC v0.1.32 (AppCard origin and formats, 2026-11-09): the closed `AppCard.kind` of four values with the new meaning of `assembled`, `origin` and `formats` with their refusals, `signOn` `idp` or `none`, the hint `wire.appcard=2` and its view-wide gate (`AppCardPublisher`, `appCardsDowngraded`), the predicates `fromOrigin` and `handles` and the three `fieldEquals` keys, the byte budget of every advertisement cache (`AdCache.DEFAULT_MAX_BYTES`, 33,554,432, and `adsRefusedCacheFull`), and the card spill of SPEC §6.1a.5 (`CardSpill`, `AppCard.Parts`, `AgentCard.Parts`, the `SpillStore` SPI with `ContentSpillStore` over the content swarm, `CardSpiller`, `DiscoveryService.resolve`, the 65,536-byte threshold and the 57,344-byte warning), in Java and in the Python, TypeScript, Ruby, and Clojure clients, with the vectors of SPEC annex I.3 in `golden.json`. The Ruby peer runs no content swarm, so it never spills a card and resolves a stub through the store its caller attaches.

Recorded with SPEC v0.1.33 (2026-11-10): Java implements the adaptive wait, asker-only repair, and flood shares of SPEC §5.3 (§5.3 above), the verified-signature memory of SPEC §11a.4 (§7.4), the ordered take's attempt window (§7.7), and the chain sources, the kept chain node, the read past superseded heads, and the two-store share of annex H (§7.8). `agentspaces-a2ui` holds the four open A2UI records of SPEC §6.1a.7 with their six vectors, and the Python and TypeScript clients read and write them. What still trails the design: no implementation cuts a chain walk's sources at a tree session's limit (`ContentPolicy.maxSessions()`, 16), so a reader that knows the versions of more than 16 writers may not ask the one that holds a node; Python's walk does not add the writers of the chain nodes it reads; a writer's swap over a merge with no base still lets the later head win whole; after one failed chain batch, a walk still backs off every later node it did not ask for (the P7 rule); Python's ordered take (`capabilities/ordered.py`) still ends at the caller's timeout; the clients' share and read paths are not yet checked for the two-store share and the superseded-head wait; a node whose lateness rings hold samples from one member alone still takes that member's wait, since the per-member cap bounds one member only once others fill the ring; and the console's `TrafficPanel` does not show `GRAFT_EVICTED_OWN` and `GRAFT_EVICTED_OTHER`. The Rust peer, which the AgentSpaces Rust team owns, is outside this record.
